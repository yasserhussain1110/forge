01ML and deep-learning foundations

The ideas every other part builds on: what a model is, how it learns from data, and the older model families that came before transformers. You need these words to read any paper or job description in the field.

1.1Tensors and building blocks

Tensor D1

An n-dimensional array of numbers: a scalar is 0-D, a vector 1-D, a matrix 2-D, and so on. Weights, activations, logits and the KV cache are all tensors.

shape · dtype · device D1–2

shape is the size of each dimension, for example [batch, seq_len, hidden]. dtype is the number format (float32, bfloat16, int8), which sets bytes per number. device is where the tensor lives (cpu or cuda:0).

WhyMost model bugs are shape bugs, memory use is shape × dtype bytes, and every op must have its inputs on the same device.

Broadcasting D2

PyTorch's rule for combining tensors of different shapes: dimensions are matched from the right, and a dimension of size 1 is stretched to match the other. A [2048] RMSNorm weight multiplies a [batch, seq, 2048] activation this way without copying.

view · reshape · transpose · permute D2

Ways to change a tensor's shape or dimension order. A view reuses the same memory with different strides; transpose/permute only change strides, so the result is often non-contiguous (not laid out in order in memory), and some ops and kernels need .contiguous() first.

WhySplitting a hidden vector into attention heads is a reshape plus a transpose. Your Triton kernels will assume a memory layout, so strides matter.

Matrix multiply (matmul) D3–4

Multiplying an (m × k) matrix by a (k × n) matrix gives (m × n) and costs about 2·m·k·n floating-point operations (FLOPs). A batched matmul does this for many matrices at once (@ on 3-D tensors).

WhyAlmost all of an LLM's compute is matmuls; every linear layer is one.

Autograd · backpropagation D8–9

Autograd records the operations that produced a value so it can compute gradients (how much each weight affected the loss) by walking backwards: backpropagation. Training needs it; inference does not.

WhyForge never trains, so it runs under torch.inference_mode() to skip that bookkeeping and save memory.

micrograd · makemore D8–13

Karpathy's teaching projects. micrograd is a ~100-line autograd engine for scalars. makemore builds character-level language models step by step: bigram counts, then an MLP, then better initialization.

MLP · linear layer · activation D11

A linear layer computes y = xW (+ b). An activation (ReLU, GELU, SiLU) is a non-linear function applied element-wise between layers. An MLP (multi-layer perceptron) is linear → activation → linear. In a transformer it is the "feed-forward" half of every block.

Softmax D6

Turns a vector of scores into probabilities that sum to 1: softmax(x)ᵢ = exp(xᵢ) / Σⱼ exp(xⱼ). It is computed as exp(xᵢ − max(x)) so large values do not overflow.

WhyUsed twice: inside attention, and to turn logits into next-token probabilities. Online softmax (section 6.4) is the trick FlashAttention is built on.

Logits D22

The raw, unnormalized score for every token in the vocabulary that the model outputs at each position. Llama 3's vocabulary has 128,256 tokens, so one position's logits are a 128,256-long vector.

Embedding (token) D11

A lookup table with one row per token ID; row i is the vector for token i. For Llama 3.2 1B it is 128,256 × 2048. It is the first thing the model does to the input IDs.

Cross-entropy · perplexity D6, D136

Cross-entropy is the average of −log p(correct next token). Perplexity is exp(cross-entropy): roughly, how many tokens the model is "choosing between" at each step. Lower is better.

WhyPerplexity on a fixed text is the quickest check that a kernel or quantization change didn't quietly damage the model.

1.2Math you will see

Vector · dot product D4, D23

A vector is a list of numbers. The dot product of two vectors multiplies them element by element and sums: a·b = Σ aᵢbᵢ. It is large when the vectors point the same way.

WhyAttention scores and embedding similarity are both dot products.

Norm (L1 · L2) not in plan

The "length" of a vector. L2 norm = sqrt(Σ xᵢ²) (ordinary distance); L1 norm = Σ |xᵢ|. Normalizing a vector means dividing it by its norm so its length is 1.

Derivative · gradient · chain rule D8

A derivative says how much an output changes when one input changes a little. A gradient is the list of derivatives with respect to every input (every weight). The chain rule multiplies derivatives through nested functions, which is exactly what backpropagation does layer by layer.

Probability distribution D10

An assignment of probabilities to every possible outcome, summing to 1. A language model's output at each step is a categorical distribution over its whole vocabulary.

Expected value · variance · standard deviation not in plan

Expected value is the probability-weighted average outcome. Variance is the average squared distance from that mean; standard deviation is its square root, in the same units as the data.

Normal (Gaussian) distribution not in plan

The bell curve, described by a mean and a standard deviation. Weights are usually initialized by drawing from one, and measurement noise is often assumed to follow one.

Sampling D39

Drawing a random outcome according to a distribution's probabilities. Generating text is repeated sampling from the model's next-token distribution (or picking the top one, which is greedy decoding).

Entropy not in plan

How uncertain a distribution is, in bits or nats: H = −Σ p log p. A model that is sure of the next token has low entropy; one spread over many tokens has high entropy.

KL divergence not in plan

A measure of how different one probability distribution is from another (zero when they are identical). Used in distillation, in RLHF to keep the tuned model close to the original, and to compare a quantized model's outputs with the original's.

Maximum likelihood not in plan

Choose the weights that make the observed data most probable. Minimizing cross-entropy on next-token prediction is exactly maximum-likelihood training of a language model.

Log probability · log-sum-exp not in plan

Probabilities of long sequences get tiny, so code works with their logarithms, which add instead of multiply. log-sum-exp computes log Σ exp(xᵢ) without overflow by subtracting the maximum first, the same trick used in a safe softmax.

Sigmoid · tanh not in plan

Squashing functions. Sigmoid maps any number to (0, 1): 1 / (1 + e⁻ˣ). tanh maps to (−1, 1). Older networks used them as activations; today sigmoid mostly appears inside gates (SiLU, LSTM) and binary classifiers.

One-hot encoding not in plan

Representing a category as a vector of zeros with a single 1 at its index. Multiplying a one-hot vector by a matrix selects one row, which is why an embedding lookup is equivalent to a matmul.

1.3Training a network

Parameters · weights · biases D8–9

The numbers a model learns. Weights multiply inputs; biases are added. "1B parameters" means about a billion such numbers. Hyperparameters, by contrast, are settings you choose before training (learning rate, batch size, number of layers).

Training · inference D9, D36

Training adjusts the weights using data and gradients. Inference runs the finished model to get outputs, with weights fixed. Training is done once (at great cost); inference happens on every request, so most production cost is inference.

WhyForge, and the whole serving field, is about inference.

Loss function D6, D9

A function that turns "how wrong were the predictions" into one number to minimize. Cross-entropy for classification and next-token prediction; mean squared error (MSE) for predicting numbers.

Training loop D9

The repeated cycle: take a batch, run the forward pass, compute the loss, call loss.backward() to get gradients, call optimizer.step() to update weights, zero the gradients, repeat.

Gradient descent D12

Move every weight a small step in the direction that reduces the loss (opposite the gradient): w ← w − lr × ∂loss/∂w. Repeated many times, the loss goes down.

Learning rate not in plan

The step size in gradient descent. Too high and training diverges (the loss blows up); too low and it barely moves. Usually the single most important hyperparameter.

SGD · mini-batch not in plan

Stochastic gradient descent estimates the gradient from a small random mini-batch of examples instead of the whole dataset. Noisier but far cheaper per step, and the noise even helps generalization.

Epoch · step · iteration not in plan

A step (or iteration) is one weight update from one batch. An epoch is one full pass through the training data. LLM pretraining usually runs about one epoch over trillions of tokens.

Batch size D44, D92

How many examples go into one gradient estimate. Larger batches give smoother gradients and use the GPU better, but need more memory. (In serving, "batch size" instead means how many requests run together.)

Momentum not in plan

An optimizer trick that keeps a running average of past gradients and steps along it, smoothing out noise and speeding progress along consistent directions.

Adam · AdamW not in plan

The standard optimizer for transformers. Adam keeps a running average of each weight's gradient (momentum) and of its squared gradient, and scales each weight's step individually. AdamW applies weight decay correctly. It stores two extra numbers per parameter, so optimizer state is often bigger than the model itself.

WhyExplains why training needs far more GPU memory than inference: weights + gradients + two Adam states, roughly 16 bytes per parameter in mixed precision.

Learning-rate schedule · warm-up · cosine decay not in plan

Changing the learning rate during training. Warm-up ramps it up from near zero over the first steps so early large gradients do not wreck the model; cosine decay then lowers it smoothly towards zero by the end.

Weight initialization D13

How weights are set before training starts. Values that are too large or small make signals explode or vanish through many layers; schemes like Xavier/Glorot and Kaiming/He scale the random draws by layer width.

Vanishing · exploding gradients D13

In deep networks, gradients multiplied through many layers can shrink to almost zero (early layers stop learning) or grow without bound (training diverges). Residual connections, normalization and careful initialization are the fixes.

Gradient clipping not in plan

If the gradient's overall norm exceeds a threshold (often 1.0), scale it down before the update. A cheap guard against sudden loss spikes.

BatchNorm D13

Normalizes each feature using statistics computed across the batch. Standard in CNNs; transformers use LayerNorm or RMSNorm instead because they normalize each token on its own, independent of what else is in the batch.

Overfitting · underfitting · generalization not in plan

Overfitting: the model memorizes training data and does worse on new data. Underfitting: it is too simple or undertrained to fit even the training data. Generalization is performance on data it has never seen, which is the thing you actually want.

Regularization · weight decay not in plan

Anything that discourages overfitting. Weight decay shrinks every weight slightly each step, keeping them small.

Dropout not in plan

During training, randomly zero a fraction of activations (say 10%) so the network cannot rely on any single unit. Turned off at inference. Many modern LLMs train with little or no dropout.

Train/validation/test split · data leakage W41

Train on one set, tune on a second, report on a third you never looked at. Leakage, where test questions sneak into training data, makes the fine-tune look better than it is.

Early stopping not in plan

Stop training when the validation loss stops improving, before the model starts to overfit.

Data loader · shuffling not in plan

The component that reads examples, shuffles their order each epoch, groups them into batches and feeds them to the GPU, ideally in background workers so the GPU never waits.

1.4Classic machine learning

Supervised · unsupervised · self-supervised learning not in plan

Supervised: learn from examples labelled with the right answer. Unsupervised: find structure in unlabelled data (clusters, compressions). Self-supervised: make labels from the data itself, such as "predict the next word". LLM pretraining is self-supervised, which is why it can use the whole internet.

Feature · label · example not in plan

An example is one data point. Its features are the inputs (columns) and its label is the answer to predict.

Feature engineering not in plan

Hand-designing input columns (ratios, counts, date parts) so a simple model can learn. Deep learning largely replaced this for text and images by learning features itself, but it still matters for tabular data.

Classification · regression not in plan

Classification predicts a category (spam or not). Regression predicts a number (a price). Next-token prediction is classification over the vocabulary.

Linear regression not in plan

Fit y = w·x + b to minimize squared error. The simplest model, and still a useful baseline.

Logistic regression not in plan

A linear model followed by a sigmoid, giving a probability for a yes/no class. Despite the name, it does classification.

Decision tree · random forest not in plan

A decision tree splits data by questions on features ("age > 30?") down to a leaf with a prediction. A random forest averages many trees trained on random subsets, which is far more accurate.

Gradient boosting · XGBoost · LightGBM not in plan

Build trees one after another, each correcting the errors of the ones before. XGBoost and LightGBM are the standard libraries and still often beat neural networks on tabular data.

k-nearest neighbours (kNN) not in plan

Predict by looking at the k most similar training examples. Vector search in RAG is the same idea at scale: find the nearest stored vectors to a query vector.

k-means clustering not in plan

Split data into k groups by repeatedly assigning points to the nearest centre and moving each centre to the mean of its points. Used inside some vector indexes (IVF).

PCA · dimensionality reduction not in plan

Dimensionality reduction compresses many features into fewer while keeping most of the information. PCA (principal component analysis) finds the directions of greatest variance and projects onto them.

t-SNE · UMAP not in plan

Methods for squashing high-dimensional vectors (embeddings) into 2-D for plotting, keeping similar points close together. Good for looking at clusters; distances in the plot are not reliable.

Bias–variance trade-off not in plan

A simple model is consistently wrong in the same way (high bias); a very flexible one changes a lot with the training sample (high variance). Good models balance the two.

Cross-validation not in plan

Split the data into k folds, train on k−1 and test on the remaining one, rotate, and average. Gives a more reliable score when data is scarce.

Confusion matrix not in plan

A table of predicted class against true class, counting true positives, false positives, true negatives and false negatives. Every classification metric is computed from it.

Precision · recall · F1 W4

Precision: of the items flagged, how many were right. Recall: of the items that should have been flagged, how many were found. F1 is their harmonic mean. Recall@k in RAG is recall restricted to the top k results.

Accuracy · class imbalance not in plan

Accuracy is the fraction of predictions that are correct. With class imbalance (say 99% of emails are not spam) it misleads: always answering "not spam" scores 99%. Use precision and recall instead.

ROC curve · AUC not in plan

The ROC curve plots true-positive rate against false-positive rate as you vary a classifier's threshold. AUC (area under it) summarizes it: 1.0 is perfect, 0.5 is random guessing.

NumPy · pandas · scikit-learn not in plan

NumPy: arrays and maths on the CPU (PyTorch tensors copy its API). pandas: tables (DataFrames) for loading and analysing data such as benchmark results. scikit-learn: the standard library of classic ML models and metrics.

1.5Neural network families

Deep learning · neural network D8

A neural network is a stack of layers, each a linear transform followed by a non-linear activation. Deep learning means networks with many layers, trained by backpropagation. LLMs are very large deep networks.

Universal approximation not in plan

The result that a large enough network with one hidden layer can approximate any reasonable function. It explains why networks can learn so much, though not how to train them efficiently.

CNN · convolution not in plan

A convolutional neural network slides small learned filters across an image, detecting edges, then textures, then objects in deeper layers. It dominated computer vision from 2012 (AlexNet) until vision transformers.

ResNet · skip connection not in plan

ResNet (2015) added skip (residual) connections, y = x + f(x), so gradients can flow straight through and networks hundreds of layers deep can train. Every transformer block uses the same trick.

RNN not in plan

A recurrent neural network reads a sequence one step at a time, carrying a hidden state forward. It cannot be parallelized across positions during training and forgets distant context, which transformers fixed.

LSTM · GRU not in plan

RNN variants with gates (small sigmoid switches) that decide what to keep, forget and output, so they remember longer. They powered machine translation and speech recognition before 2017.

Seq2seq · encoder–decoder D16

An encoder reads the whole input into a representation; a decoder generates the output from it, token by token. The original transformer and translation models (and T5, Whisper) use this layout.

Attention (before transformers) D16

Bahdanau attention (2014) let a translation decoder look back at every encoder state with learned weights, instead of squeezing the input into one fixed vector. Transformers kept attention and dropped the recurrence.

Word2vec · word embeddings not in plan

Word2vec (2013) learned a vector per word by predicting nearby words, so similar words got similar vectors ("king − man + woman ≈ queen"). The ancestor of every embedding model.

Representation · latent space not in plan

The internal vectors a network computes. The latent space is the space those vectors live in, where nearby points mean similar things.

Autoencoder · VAE not in plan

An autoencoder compresses its input to a small latent vector and reconstructs it. A VAE (variational autoencoder) makes that latent space smooth so you can sample new data from it. Image generators such as Stable Diffusion use a VAE to move between pixels and latents.

GAN not in plan

A generative adversarial network: a generator makes fake samples and a discriminator tries to tell them from real ones; each improves against the other. State of the art for images before diffusion models.

Transfer learning · pretrained model not in plan

Train a big model once on general data (pretraining), then adapt it to a specific task with much less data. LLM fine-tuning is transfer learning.

Foundation model not in plan

A large model pretrained on broad data that many applications build on (GPT, Claude, Llama, Gemini). The term emphasizes reuse rather than architecture.

Reinforcement learning · policy · reward not in plan

Learning by trial and error: an agent following a policy takes actions in an environment and receives rewards; training makes high-reward actions more likely. RLHF and reasoning-model training apply it to LLMs, where the policy is the model and an action is a generated token or answer.

02Transformer and LLM architecture

What is inside a large language model: the transformer, the Llama design Forge implements, the variants other labs use, and how models handle long inputs. Forge's model code lives here; the rest of the field's architectures are here so none of them is a surprise.

2.1Transformers, tokens and Llama models

Transformer D15–17

The architecture from Attention Is All You Need (2017): a stack of identical blocks, each with an attention layer (tokens look at each other) and an MLP (each token processed on its own), joined by residual connections.

Decoder-only model D22

A transformer that only predicts the next token, using a causal mask so position i can only attend to positions ≤ i. GPT and Llama are decoder-only. The original transformer also had an encoder; LLMs dropped it.

Autoregressive generation D22, D33

Generate one token, append it to the input, run the model again, repeat. Each new token depends on all earlier ones, so decode steps for one sequence can't run in parallel.

WhyThis is why decode is slow and why most of the serving tricks exist.

Tokenizer · token · BPE D20

A tokenizer maps text to integer IDs (tokens) and back. BPE (byte-pair encoding) builds the vocabulary by repeatedly merging the most frequent adjacent pair of byte sequences. Llama 3 uses a tiktoken-style BPE with 128,256 tokens; one English word is about 1.3 tokens.

tiktoken D20

OpenAI's fast BPE library. Llama 3's tokenizer is built on the same approach. In Forge you will normally load it through Hugging Face's tokenizers/AutoTokenizer.

Special tokens · EOS D33, D40

Reserved tokens with meaning, not text: <|begin_of_text|>, <|start_header_id|>, and the end tokens. Llama 3 Instruct ends a turn with <|eot_id|>. An EOS (end-of-sequence) token tells the engine to stop.

WhyMissing <|eot_id|> from your stop set is the classic "model never stops talking" bug.

Chat template D33, D51

The exact text format that wraps a list of chat messages (system/user/assistant) in special tokens before tokenizing. It ships as a Jinja template in tokenizer_config.json and is applied with apply_chat_template.

WhyYour /v1/chat/completions endpoint must apply it exactly, or answer quality drops sharply.

Llama 3.2 1B / 3B D29 onward

Meta's small Llama models, the ones Forge runs. 1B: 16 layers, hidden size 2048, 32 query heads, 8 KV heads, head dim 64, about 2.5 GB in bf16. 3B: 28 layers, hidden 3072, 24 query heads, 8 KV heads, head dim 128, about 6.4 GB in bf16. Both fit in 8 GB.

Llama 3.1 8B D131, D145

32 layers, hidden 4096, 32 query heads, 8 KV heads. About 16 GB in bf16, so it doesn't fit your 4060. That's why it appears only on rented GPUs (speculative decoding target, two-GPU tensor parallelism).

The Llama 3 Herd of Models D26

Meta's Llama 3 paper: architecture, training data, scaling, and the long-context RoPE scaling recipe.

config.json D29

The model's hyperparameters: num_hidden_layers, hidden_size, num_attention_heads, num_key_value_heads, rope_theta, rope_scaling, rms_norm_eps, tie_word_embeddings. Forge builds its model from these values.

fp32 · fp16 · bf16 D29

Floating-point formats. fp32: 4 bytes. fp16: 2 bytes, 5 exponent bits, so it overflows above ~65,504. bf16 (brain float): 2 bytes, 8 exponent bits like fp32 (same range) but only 7 mantissa bits (less precision).

WhyForge runs in bf16, so 1 parameter = 2 bytes. Reductions like the RMSNorm mean are done in fp32 for accuracy.

Qwen · Mistral · Gemma not in plan

Other open model families with nearly Llama-shaped architectures. Supporting a second family in Forge is a good test of how general your loader and layers really are.

2.2Llama architecture

Residual stream · pre-norm D27

Each block does x = x + attn(norm(x)) then x = x + mlp(norm(x)). The running x is the residual stream. Pre-norm means normalizing before each sub-layer, not after (GPT-2 and Llama both do this).

RMSNorm D24, D30, D74

y = x / sqrt(mean(x²) + ε) · g, where g is a learned per-channel weight and ε = 1e-5 for Llama 3. Unlike LayerNorm there is no mean subtraction and no bias, so it is cheaper.

WhyYour first layer tested against HF and your first fused Triton kernel. Compute the mean of squares in fp32.

LayerNorm D24

GPT's normalization: subtract the mean, divide by the standard deviation, then scale and shift. It shows you what RMSNorm removed.

SwiGLU · SiLU D24, D30, D75

Llama's MLP: down( silu(gate(x)) * up(x) ), with three weight matrices instead of two. SiLU is x · sigmoid(x). For Llama 3.2 1B the intermediate size is 8192, four times the hidden size.

Attention · Q, K, V D16–18

Each token's hidden vector is projected to a query (what am I looking for), a key (what do I contain) and a value (what I pass on). Output = softmax(QKᵀ / √d) · V: each token takes a weighted average of earlier tokens' values, weighted by how well its query matches their keys.

Head · head dim D18, D25

Attention runs in several independent heads in parallel, each on a slice of size head dim. Llama 3.2 1B: 32 heads × 64 = 2048.

MHA · MQA · GQA D25, D31

Multi-head attention: every query head has its own K and V heads. Multi-query: all query heads share one K/V head. Grouped-query: query heads are split into groups and each group shares a K/V head. Llama 3.2 1B has 32 query heads sharing 8 KV heads (groups of 4).

WhyGQA makes the KV cache 4× smaller than MHA would. In code it's a repeat_kv or a reshape so each KV head serves its group.

RoPE (rotary position embeddings) D23, D31, D75

Encodes position by rotating each pair of dimensions in q and k by an angle position × θᵢ, where θᵢ = base^(−2i/d). Because both are rotated, the q·k score depends only on the distance between tokens. Llama 3 uses base (rope_theta) 500,000 plus a "llama3" frequency scaling for long context.

WhyThe commonest mismatch with HF: HF pairs dimension i with i + d/2 ("rotate_half"), not adjacent dimensions. You must also apply the scaling exactly.

RoFormer D23

The paper that introduced RoPE. EleutherAI's blog post on rotary embeddings is the friendlier read.

lm_head · tied embeddings D32

The lm_head is the final linear layer from hidden size to vocabulary size, producing logits. Tied embeddings means it reuses the input embedding matrix. Llama 3.2 1B and 3B are tied, so the file has no separate lm_head.weight.

Causal mask D18

A mask that sets attention scores for future positions to −∞ before softmax, so they get zero weight. In decode with a KV cache the single new query can see everything cached, so no mask is needed.

2.3Architecture variants

Encoder-only model · BERT not in plan

A transformer with bidirectional attention (every token sees every other, no causal mask), trained to fill in masked words. Good at understanding text, not at generating it. BERT (2018) and its descendants power most embedding models and rerankers.

Encoder–decoder model · T5 not in plan

The original transformer layout: an encoder reads the input bidirectionally, a decoder generates output while attending to it (cross-attention). T5 and BART are text examples; Whisper uses it for speech.

GPT-2 architecture D22

OpenAI's 2019 decoder-only model and the usual teaching example (nanoGPT). Compared with Llama it uses learned absolute position embeddings, LayerNorm, GELU MLPs and full multi-head attention.

Absolute vs relative positions D23

Attention by itself ignores order, so position must be injected. Absolute schemes add a per-position vector to the input (learned, or sinusoidal in the original transformer). Relative schemes (RoPE, ALiBi) make attention depend on the distance between tokens, which extends better to longer inputs.

ALiBi not in plan

Attention with linear biases: no position embeddings at all; instead each attention score gets a penalty proportional to the distance between the two tokens. Used by BLOOM and MPT.

Dense model · sparse model · active parameters not in plan

In a dense model every parameter is used for every token. In a sparse (MoE) model only some experts run per token. Active parameters is the count actually used per token; it sets compute, while total parameters sets memory. DeepSeek-V3 has 671B total and 37B active.

WhyFor serving, an MoE model needs memory like a big model but compute like a small one.

MoE (mixture of experts) not in plan

A model where each block's MLP is replaced by many "expert" MLPs plus a small router that sends each token to its top-k experts (e.g. 2 of 64). Lots of parameters, little compute per token. Mixtral, DeepSeek-V3 and Qwen3-MoE use it, and it comes up constantly in inference interviews.

Router · top-k gating not in plan

The small layer in an MoE block that scores every expert for each token and sends the token to the top-k (often 2 or 8). The outputs of the chosen experts are summed, weighted by the router's scores.

Load balancing (MoE) not in plan

If the router sends most tokens to a few experts, those become bottlenecks and the rest are wasted. Training adds an auxiliary loss or bias adjustments that push towards an even spread; at serving time imbalance shows up as uneven GPU load.

Shared experts · fine-grained experts not in plan

DeepSeek-style MoE design: many small experts instead of a few big ones (fine-grained), plus one or more shared experts that every token always uses for common knowledge.

MLA (multi-head latent attention) not in plan

DeepSeek's attention variant that compresses keys and values into a small shared latent vector per token and stores only that in the KV cache, shrinking the cache far more than GQA while keeping quality.

WhyAn inference-driven design choice: KV cache size, not FLOPs, limited DeepSeek's serving.

Sliding-window attention not in plan

Each token attends only to the last W tokens (say 4,096) instead of all of them, so the KV cache stops growing past W. Mistral 7B used it; Gemma alternates sliding-window layers with full-attention layers.

Sparse attention not in plan

Any scheme where each token attends to a chosen subset of earlier tokens (local windows, strided patterns, or positions picked by a learned selector, as in DeepSeek's sparse attention) instead of all of them, to cut the quadratic cost of long contexts.

Linear attention not in plan

Attention reformulated so its cost grows linearly with sequence length, usually by replacing softmax with a kernel feature map so the sum over past tokens becomes a running state. Cheaper, but historically weaker at exact recall.

State-space model (SSM) · Mamba not in plan

A sequence model that, like an RNN, carries a fixed-size state from token to token, but is designed so training still runs in parallel. Mamba (2023) made the state update depend on the input ("selective"). Decode cost per token is constant and there is no KV cache that grows.

Hybrid models not in plan

Models that mix a few full-attention layers with many SSM or linear-attention layers (Jamba, Zamba, Qwen3-Next, Nemotron-H). They aim for transformer quality with much smaller memory per token at long context.

RWKV not in plan

An open RNN-style architecture that trains in parallel like a transformer and decodes with constant memory. A long-running alternative-architecture project.

QK-norm not in plan

Applying a normalization (often RMSNorm) to queries and keys before the attention dot product. It keeps attention logits from growing huge and stabilizes training; used in Gemma 3, Qwen3 and OLMo 2.

Logit soft-capping not in plan

Squashing logits through cap · tanh(x / cap) so no value exceeds the cap. Gemma 2 used it on attention scores and final logits; it changes which attention kernels can run the model.

Multi-token prediction (MTP) not in plan

Training extra heads to predict tokens two or more steps ahead, not just the next one. It improves training signal, and at inference the extra heads can serve as a built-in draft model for speculative decoding (DeepSeek-V3).

Byte-level and tokenizer-free models not in plan

Models that read raw bytes instead of a fixed vocabulary, often grouping bytes into patches on the fly (Meta's Byte Latent Transformer). They avoid tokenizer quirks such as poor handling of numbers and rare languages.

Diffusion language models not in plan

Text models that generate by starting from a fully masked sequence and filling in many tokens in parallel over several refinement steps, instead of one token at a time left to right (for example LLaDA, Gemini Diffusion, Mercury). Still a minority approach; they change the serving problem completely.

2.4Long context

Context length · max_position_embeddings D11, D40

The maximum number of tokens (prompt plus output) a model was trained to handle; max_position_embeddings in config.json. Llama 3.2 supports 131,072 tokens. Beyond it, quality collapses.

WhyYour engine's real limit is usually KV cache memory, far below the model's limit on an 8 GB GPU.

Context extension · position interpolation not in plan

Making a model trained on short sequences work on longer ones. Position interpolation squeezes new, longer positions into the range the model saw in training by scaling positions down, then fine-tunes briefly.

NTK-aware scaling · YaRN · Llama 3 RoPE scaling D31

Smarter ways to stretch RoPE: rotate high-frequency dimensions as before (local order) and stretch only the low-frequency ones (long distances). YaRN is a popular recipe; Llama 3.1+ uses its own variant described by rope_scaling in the config, which Forge must reproduce exactly.

Needle in a haystack not in plan

A long-context test: hide one fact (the needle) at some depth inside a long, irrelevant document and ask for it. A heat-map over length and depth shows where retrieval fails. Easy to pass; real long-context use is harder.

RULER · effective context length not in plan

RULER is a benchmark of harder synthetic long-context tasks (multiple needles, tracing variables, aggregation). It shows that a model's effective context length, where it still performs well, is often much shorter than its advertised one.

Attention sink · StreamingLLM not in plan

Models dump a lot of attention onto the first few tokens regardless of content (attention sinks). StreamingLLM keeps those first tokens plus a recent window in the KV cache, letting a model run on endless streams with fixed memory.

KV cache compression · eviction not in plan

Dropping or shrinking KV cache entries that matter least, for example tokens that receive little attention (H2O, SnapKV), or storing them in fewer bits. Trades a little quality for a lot more context or batch per GPU.

Long context vs RAG not in plan

With million-token context windows you can sometimes paste the whole document set into the prompt instead of retrieving. Trade-off: simpler, but slower, costlier per request, and models still miss details in very long inputs. Prefix caching makes repeated long contexts cheaper.

2.5Looking inside the model

Interpretability · mechanistic interpretability not in plan

Interpretability asks why a model produced an output. Mechanistic interpretability reverse-engineers the actual computation: which neurons, heads and directions carry which information.

Features · superposition not in plan

A feature is a concept the model represents (say "Python code" or "the Golden Gate Bridge"), usually as a direction in activation space. Superposition: models pack far more features than they have neurons by overlapping them, so single neurons rarely mean one thing.

Sparse autoencoder (SAE) not in plan

A small network trained to rewrite a model's activations as a sparse combination of many learned features, untangling superposition into human-readable concepts. Anthropic, OpenAI and Google DeepMind all use them.

Circuits · induction heads not in plan

A circuit is a group of components that together implement a behaviour. Induction heads are a famous one: attention heads that find an earlier occurrence of the current token and copy what followed it, a key mechanism behind in-context learning.

Logit lens · probing not in plan

Logit lens: apply the final unembedding to intermediate layers' hidden states to see what the model "would predict" partway through. Probing: train a small classifier on activations to test whether some information (say, sentiment) is present there.

Activation steering · steering vectors not in plan

Add a chosen direction to a model's activations at inference time to push its behaviour, for example towards a topic or away from refusals, without changing any weights.

Attribution graphs not in plan

Diagrams tracing which internal features caused an output, step by step through the layers, so you can follow a model's reasoning on one prompt. Anthropic's "tracing thoughts" work popularized them.

Grokking not in plan

A training curiosity: a small model memorizes its training set, then much later suddenly generalizes, with test accuracy jumping long after training loss has flattened.

03Training and post-training

How a model gets its weights: pretraining on huge text corpora, then post-training that turns a text predictor into a helpful assistant, then the fine-tuning you might do yourself. You will not train a large model in this plan, but every model you serve was made this way, and interviewers will ask.

3.1Pretraining

Pretraining not in plan

The first and by far most expensive stage: train a randomly initialized model to predict the next token on trillions of tokens of general text. The result, a base model, knows a lot but only continues text; it does not follow instructions.

Pretraining corpus · Common Crawl not in plan

The text a model is pretrained on. Common Crawl, a free monthly scrape of the public web, is the raw source of most of it, alongside code (GitHub), books, papers and Wikipedia. Llama 3 was trained on about 15 trillion tokens.

FineWeb · The Pile · Dolma · RedPajama not in plan

Public, cleaned pretraining datasets. FineWeb (Hugging Face) is a filtered 15T-token Common Crawl set; The Pile, Dolma (AI2) and RedPajama are earlier mixed-source sets. They let researchers reproduce pretraining openly.

Data filtering · quality classifiers not in plan

Removing junk (spam, boilerplate, low-quality or toxic pages) before training, often with a small classifier trained to score "educational" or "high-quality" text. Data quality now matters as much as model size.

Data deduplication · MinHash not in plan

Removing duplicate and near-duplicate documents so the model does not memorize repeated text. MinHash estimates how much two documents overlap without comparing them in full, which makes this feasible across billions of pages.

Data mixture not in plan

The proportions of each source in training (say 50% web, 25% code, 10% maths...). Tuning the mix changes what the model is good at as much as architecture does.

Scaling laws not in plan

Empirical rules that loss falls predictably, as a power law, as you increase parameters, data and compute. They let labs predict a big model's quality from small experiments before spending the money.

Chinchilla · compute-optimal training not in plan

DeepMind's 2022 finding that for a fixed compute budget, parameters and training tokens should grow together, about 20 tokens per parameter. Earlier large models were undertrained by that rule.

Over-training (inference-optimal) not in plan

Training a small model on far more tokens than Chinchilla suggests (Llama 3 8B saw about 1,900 tokens per parameter). It costs more training compute but gives a better model per parameter, which is cheaper to serve forever after.

WhyShows how inference cost shapes training decisions.

Training compute · 6ND not in plan

Rule of thumb: training costs about 6 × N × D FLOPs for N parameters and D tokens (2ND for the forward pass, 4ND for the backward). Inference costs about 2N FLOPs per token.

Emergent abilities not in plan

Skills (multi-step arithmetic, following instructions) that seem to appear suddenly once models pass some size. Later work showed many look sudden only because of all-or-nothing metrics; with smoother metrics they improve gradually.

Loss curve · loss spike not in plan

The plot of training loss over steps. A loss spike is a sudden jump, often from instability in very large runs; teams roll back to an earlier checkpoint and skip the offending data or lower the learning rate.

Training checkpoint not in plan

A saved snapshot of weights, optimizer state and data position, written regularly so a crashed run can resume. The released model is one chosen checkpoint, usually converted to safetensors.

Mixed-precision training not in plan

Doing most maths in bf16 (or FP8) for speed while keeping a master copy of the weights and some reductions in fp32 for accuracy. Standard for all large training.

Gradient accumulation not in plan

Simulating a large batch on limited memory: run several small batches, add up their gradients, and only then take one optimizer step.

Activation checkpointing not in plan

Also called gradient checkpointing. Instead of storing every layer's activations for the backward pass, store only some and recompute the rest when needed. Trades about 30% more compute for much less memory.

Mid-training · annealing not in plan

A shorter stage at the end of pretraining, on higher-quality and specialized data (maths, code, long documents) with the learning rate decaying to zero. Often where long-context ability is added.

Continued pretraining not in plan

Taking an existing base model and pretraining further on new data, for example a language or domain the original saw little of, before any instruction tuning.

3.2Post-training

Base model · instruct model W42

A base model only continues text ("The capital of France is" → "Paris. The capital of..."). An instruct (chat) model has been post-trained to follow instructions and stop at the end of its turn. Forge serves the Instruct variants.

Post-training not in plan

Everything after pretraining that shapes behaviour: supervised fine-tuning, preference tuning, reinforcement learning, and safety training. Cheap compared with pretraining, but it decides how helpful, safe and well-formatted the model is.

SFT (supervised fine-tuning) · instruction tuning not in plan

Train on example conversations (prompt plus ideal answer) with the ordinary next-token loss. Instruction tuning is SFT on many diverse tasks phrased as instructions, so the model learns to follow instructions in general.

Preference data · chosen / rejected not in plan

Pairs of answers to the same prompt, labelled by humans or a model as chosen (better) and rejected (worse). The raw material for reward models and DPO.

Reward model not in plan

A model trained on preference data to output a score for how good an answer is. It stands in for a human judge during reinforcement learning.

RLHF (reinforcement learning from human feedback) not in plan

The recipe behind ChatGPT: train a reward model on human preferences, then use reinforcement learning to make the LLM produce answers the reward model scores highly, while a KL penalty keeps it close to the SFT model so it does not drift into nonsense.

PPO not in plan

Proximal policy optimization, the RL algorithm classic RLHF uses. It updates the model in small, clipped steps and needs a separate value model, so four models are in memory at once (policy, reference, reward, value).

DPO (direct preference optimization) not in plan

Skips the reward model and RL loop: a simple loss directly raises the probability of chosen answers relative to rejected ones. Much easier to run than PPO, so it became the default for open models. KTO, ORPO and SimPO are variants.

RLAIF · Constitutional AI not in plan

RLAIF: reinforcement learning from AI feedback, where a model, not a human, labels which answer is better. Constitutional AI (Anthropic) has the model critique and revise answers against a written list of principles, the constitution, and trains on the results.

RLVR (verifiable rewards) not in plan

Reinforcement learning where the reward comes from an automatic checker, not a judge: did the maths answer match, did the code pass its tests. Because the reward cannot be fooled as easily, it scales to long training and is how reasoning models are made.

GRPO not in plan

Group relative policy optimization (DeepSeek): sample several answers per prompt, score them, and push the model towards answers better than the group's average. No value model is needed, so it is cheaper than PPO. Used to train DeepSeek-R1.

Reasoning models · long chain of thought not in plan

Models trained with RL to "think" at length (thousands of hidden or visible tokens) before answering: OpenAI's o-series, DeepSeek-R1, Claude's extended thinking, Gemini thinking models. Much better at maths and code; much more output tokens per request.

WhyShifts serving load towards long decodes, making TPOT and KV cache size matter even more.

Outcome vs process reward model not in plan

An outcome reward model scores only the final answer. A process reward model (PRM) scores each reasoning step, giving finer feedback and a way to pick the best partial reasoning path.

Rejection sampling · best-of-n not in plan

Generate n answers, keep the best by some score (reward model or checker). Used both at inference time to improve answers and in training, where the kept answers become new SFT data. (Not the same rejection sampling as in speculative decoding, which is a sampling-correction rule.)

Reward hacking not in plan

The model finds a way to score highly that the designers did not intend: overly long answers if the judge likes length, or editing tests so code "passes". A central problem in RL training and in evals.

Distillation · teacher / student not in plan

Train a small student model to imitate a large teacher, either on the teacher's generated answers or on its full output probabilities. Most small models (Llama 3.2 1B/3B among them) were trained partly this way.

Synthetic data · self-instruct not in plan

Training data generated by models instead of people: questions, answers, reasoning traces, critiques. Self-instruct had a model write its own instruction dataset. Now a large share of post-training data.

Model collapse not in plan

Quality degradation when models are trained repeatedly on their own (or other models') outputs without fresh human data: the rare parts of the distribution disappear. A reason synthetic data is mixed carefully.

Model merging · model soup not in plan

Combining the weights of several fine-tuned versions of the same base model, by averaging or smarter methods (TIES, DARE, SLERP), into one model that keeps several skills. No extra training needed.

Alignment tax not in plan

The loss of raw capability that safety and preference training can cause, for example a model becoming worse at some benchmarks or over-refusing. Good post-training aims to keep it small.

3.3Fine-tuning in practice

When to fine-tune not in plan

Try in this order: better prompts, then RAG for knowledge, then fine-tuning. Fine-tune to change behaviour (format, tone, a narrow task, a smaller cheaper model doing what a big one did), not to add facts, which RAG does better and keeps up to date.

Full fine-tuning not in plan

Updating every weight of the model. Best quality, but needs memory for gradients and optimizer state (about 16 bytes per parameter), so even an 8B model needs several large GPUs.

LoRA · PEFT W41

LoRA (low-rank adaptation) freezes the base weights W and trains a small update ΔW = B·A with rank r of about 8–16, roughly 0.1–1% of the parameters. That's why fine-tuning Llama 3.2 1B fits in 8 GB. PEFT is Hugging Face's library for it.

QLoRA not in plan

LoRA on top of a 4-bit quantized base model, so even bigger models can be fine-tuned on small GPUs.

LoRA rank · alpha · target modules W41

LoRA's settings. Rank r is the size of the small matrices (8–64 typical); alpha scales their effect; target modules lists which weight matrices get adapters (often all attention and MLP projections).

Merging an adapter not in plan

Adding a LoRA's update permanently into the base weights (W + BA), giving an ordinary model with no extra inference cost. The alternative is to keep adapters separate and swap them per request.

Adapters · prefix tuning · prompt tuning not in plan

Earlier PEFT methods. Adapters insert small extra layers; prefix and prompt tuning learn a few "virtual token" vectors prepended to the input while the model stays frozen.

Catastrophic forgetting not in plan

Fine-tuning on a narrow task can erase general abilities the model had. Mitigated by small learning rates, LoRA, and mixing some general data back in.

Chat-format dataset · JSONL W41

Fine-tuning data is usually a JSONL file (one JSON object per line), each a list of messages with roles, exactly like an API request. It must be rendered with the model's own chat template.

Loss masking not in plan

Computing the loss only on the assistant's tokens, not the prompt's, so the model learns to answer rather than to imitate questions.

Sequence packing not in plan

Concatenating several short training examples into one long sequence (with attention kept separate between them) so no compute is wasted on padding. The training-side cousin of packed varlen prefill.

TRL · Unsloth · Axolotl · torchtune not in plan

Fine-tuning tools. TRL (Hugging Face): SFT, DPO, GRPO trainers. Unsloth: fast, memory-light LoRA/QLoRA that fits small models on consumer GPUs like yours. Axolotl and LLaMA-Factory: config-file driven training. torchtune: PyTorch's own recipes.

Hosted fine-tuning APIs not in plan

Upload a dataset and get a fine-tuned model back, without managing GPUs: OpenAI, Google Vertex AI, Amazon Bedrock, Together, Fireworks and others offer it.

Embedding fine-tuning · contrastive loss · hard negatives not in plan

Training an embedding model on (query, relevant passage) pairs with a contrastive loss that pulls matching pairs together and pushes others apart. Hard negatives are passages that look relevant but are not; including them helps most. Often the best way to improve retrieval in a narrow domain.

04Model landscape and ecosystem

Who makes the models, how they are released, where you download them, and who sells access to them. Names change quickly here; the categories do not. This list is accurate as of mid-2026.

4.1Kinds of models

Frontier model not in plan

The most capable models available at a given time, from the few labs that can afford the largest training runs. "Frontier" is relative and shifts every few months.

Closed (proprietary) model W3

A model you can only use through its maker's API or app; the weights are never released (GPT, Claude, Gemini). You pay per token and cannot run it yourself.

Open-weight model D29

A model whose trained weights you can download and run yourself (Llama, Qwen, Mistral, DeepSeek, Gemma). Usually the training data and code are not released, so "open weights" is more accurate than "open source".

Open-source model (fully open) not in plan

A model released with its weights, training code and training data, so it can be reproduced: AI2's OLMo, Hugging Face's SmolLM, EleutherAI's Pythia.

Model licence D29

The terms attached to open weights. Apache 2.0 and MIT allow almost anything (Qwen, Mistral's open models, DeepSeek). The Llama Community Licence adds conditions, such as a cap on very large companies and naming rules. Check it before building a product on a model.

Model card not in plan

The README for a model: what it is for, how it was trained, benchmark scores, limitations, licence. On Hugging Face it is the repo's front page.

Small language model (SLM) not in plan

Models of roughly 0.5–8B parameters (Llama 3.2 1B/3B, Phi, Gemma, Qwen small sizes, SmolLM) meant to run cheaply, on one consumer GPU, a laptop or a phone. Often distilled from larger models.

Chat · instruct · base · reasoning variants not in plan

One model family usually ships several variants: base (pretrained only), instruct or chat (post-trained to follow instructions), and sometimes a reasoning or "thinking" variant, plus quantized versions. Names like Llama-3.2-1B-Instruct tell you which.

Model size naming (7B, 70B, 8x7B, A3B) not in plan

The B number is billions of parameters. MoE models are named by experts or by active parameters: Mixtral 8x7B (eight experts of about 7B each), Qwen3-30B-A3B (30B total, 3B active).

Knowledge cutoff not in plan

The date after which a model's training data stops, so it knows nothing newer unless you supply it in the prompt (RAG, web search tools).

4.2Labs and model families

OpenAI · GPT · o-series D51

Maker of ChatGPT. Families: GPT (GPT-4, GPT-4o, GPT-4.1, GPT-5 and later), and the o-series reasoning models (o1, o3, o4-mini). Also released open-weight gpt-oss models in 2025. Its API format became the de facto standard Forge copies.

Anthropic · Claude not in plan

Maker of the Claude models, in sizes named Haiku (small, fast), Sonnet (middle) and Opus (largest). Known for coding and agent use, Constitutional AI and interpretability research. Also created MCP.

Google · Gemini · Gemma D179

Google DeepMind's closed Gemini models (very long context, natively multimodal) and open-weight Gemma models. Google also designs its own chips (TPUs) and wrote the original transformer paper.

Meta · Llama D26

Meta's open-weight family: Llama 2 (2023), Llama 3 / 3.1 / 3.2 / 3.3 (2024), Llama 4 (2025, MoE). Llama 3 made the dense GQA + RoPE + SwiGLU design the standard that most open models copy, which is why Forge targets it.

Mistral AI not in plan

French lab with open-weight models (Mistral 7B, Mixtral MoE, Mistral Small) and commercial ones (Mistral Large, Codestral). Mistral 7B popularized sliding-window attention and Mixtral popularized open MoE.

Qwen (Alibaba) not in plan

Alibaba's open-weight family (Qwen2.5, Qwen3, Qwen3-Coder and more), in sizes from about 0.6B to 235B+ including MoE, Apache-2.0 licensed and among the most used open models. Qwen's dense models are close to Llama in shape, so they are the natural second family to add to Forge.

DeepSeek not in plan

Chinese lab whose open-weight DeepSeek-V3 (MoE with MLA attention) and DeepSeek-R1 (reasoning, trained with GRPO) matched frontier models at a fraction of the reported cost in early 2025. Its papers are among the best sources on efficient training and serving.

Microsoft · Phi not in plan

Microsoft's Phi small models, trained heavily on curated and synthetic "textbook-quality" data to punch above their size.

xAI · Grok not in plan

Elon Musk's lab and its Grok models, offered through X and an API.

NVIDIA Nemotron · Cohere Command · AI2 OLMo not in plan

Other notable families. Nemotron: NVIDIA's open models and open datasets, many derived from Llama or hybrid Mamba designs. Command: Cohere's enterprise models, focused on RAG and tool use. OLMo: AI2's fully open models.

Moonshot Kimi · Zhipu GLM · MiniMax not in plan

Other Chinese labs releasing large open-weight models (Kimi K2, GLM-4.5, MiniMax-M1), many of them MoE and strong at coding and agents.

4.3Hubs, formats and libraries

Hugging Face Hub · huggingface_hub D29

The website that hosts model weights and configs, and the Python library that downloads them (snapshot_download). Llama repos are gated: you accept Meta's licence and use an access token.

transformers D26, D30

Hugging Face's library of reference model implementations. LlamaForCausalLM in modeling_llama.py is the ground truth Forge is tested against, layer by layer.

safetensors D29

The weight file format: a JSON header (each tensor's name, dtype, shape, byte offset) followed by raw bytes. Safe because unlike pickle it can't run code, and fast because it can be memory-mapped.

Hugging Face Datasets not in plan

The datasets library and the Hub's dataset repositories: download, stream and process benchmark and training data (MMLU, ShareGPT, FineWeb) with one call.

Hugging Face Spaces not in plan

Free hosting on the Hub for small demo apps (Gradio or Streamlit). A common way to give a project a clickable demo.

Gradio · Streamlit not in plan

Python libraries that turn a function into a simple web UI in a few lines. Handy for a quick chat demo in front of your API.

GGUF · GGML not in plan

GGUF is llama.cpp's single-file model format: weights (often 2–8-bit quantized, with names like Q4_K_M) plus tokenizer and metadata. GGML is the C tensor library under llama.cpp. Most laptop users run models as GGUF files.

ONNX · ONNX Runtime not in plan

ONNX is a framework-neutral file format for neural network graphs; ONNX Runtime runs them on many kinds of hardware. More common for small models and edge devices than for LLM serving.

MLX not in plan

Apple's array framework for Apple-silicon Macs, with an LLM package (mlx-lm). The usual way to run and fine-tune models efficiently on a Mac.

LM Studio · Jan · Open WebUI not in plan

Desktop and web front-ends for running and chatting with local models, built on llama.cpp, MLX or any OpenAI-compatible server. Open WebUI can point at your Forge server.

Leaderboards not in plan

Public rankings of models: LMArena (human votes), Artificial Analysis (quality, speed and price per provider), the Open LLM Leaderboard and many task-specific ones. Useful for shortlisting, but scores are gamed and contaminated, so run your own evals.

4.4APIs and providers

Model API · chat completions D51

Paying a provider to run a model and calling it over HTTP. Most share OpenAI's /v1/chat/completions shape (messages in, message out); Anthropic's Messages API and Google's Gemini API differ in details such as how system prompts and tool calls are written.

Responses API not in plan

OpenAI's newer stateful API that can keep conversation state on the server and run built-in tools (web search, file search, code interpreter) in one call. Chat completions remains the common compatibility format.

Price per million tokens W26

How APIs charge: separate prices for input tokens and (several times higher) output tokens, plus discounts for cached input. Cost = input tokens × input price + output tokens × output price.

WhyThe number your gateway's cost tracking and Forge's cost-per-token comparison are built on.

Rate limits · RPM · TPM W29

Providers cap how much you can send: RPM (requests per minute) and TPM (tokens per minute), per account tier. Hitting one returns HTTP 429, which clients should retry with backoff.

Batch API not in plan

Submit a file of many requests and get results within hours (often 24h) at around half price. Good for evals, data labelling and other offline work that does not need instant answers.

Prompt caching (API feature) not in plan

Providers charge much less (and answer faster) for input tokens that repeat a previous request's prefix, such as a long system prompt. Under the hood it is prefix caching. Some providers make it automatic; Anthropic's needs explicit cache-control markers.

Cloud AI platforms: Bedrock · Vertex AI · Azure AI Foundry not in plan

The big clouds' model services. Amazon Bedrock, Google Vertex AI and Microsoft Azure AI Foundry (including Azure OpenAI) sell access to many vendors' models with the cloud's billing, security and data-residency guarantees. Enterprises often must use these.

Inference providers: Together · Fireworks · Groq · Cerebras · DeepInfra D179

Companies that serve open-weight models over OpenAI-compatible APIs, competing on price and speed. Groq and Cerebras use their own chips for very high tokens per second. These are companies like the one Forge's skills target.

Model aggregators · OpenRouter not in plan

One API key and endpoint that routes to hundreds of models from many providers, with unified billing and fallbacks. A hosted version of what your gateway does.

Token counting · usage field D51

Every response reports usage: prompt and completion tokens (and cached and reasoning tokens where relevant). Tokenizers differ between models, so the same text costs a different number of tokens on each.

05Prompting and LLM app building

How applications talk to models: writing prompts, controlling generation, getting structured output back, and the libraries people build LLM apps with. This is the everyday vocabulary of "AI engineer" job posts, and the client side of the API Forge serves.

5.1Prompting

Prompt D33

Everything the model sees before it generates: system instructions, conversation history, retrieved documents, tool results and the user's message, all rendered into one token sequence by the chat template.

System prompt · roles D113

Chat messages carry a role: system (the developer's standing instructions), user, assistant (the model's earlier replies) and tool (results of tool calls). The system prompt sets persona, rules and format for the whole conversation.

Zero-shot · few-shot not in plan

Zero-shot: ask for the task with no examples. Few-shot: include a handful of worked input→output examples in the prompt so the model copies the pattern and format.

In-context learning not in plan

A model's ability to pick up a task from examples or instructions in the prompt alone, with no weight updates. Discovered with GPT-3 (2020); it is why prompting works at all.

Chain-of-thought (CoT) not in plan

Asking the model to reason step by step before giving its answer ("think step by step"), which improves accuracy on maths and logic. Reasoning models are trained to do this by themselves.

Self-consistency not in plan

Sample several chain-of-thought answers at non-zero temperature and take the most common final answer. Trades extra compute for accuracy.

Tree of thoughts not in plan

Exploring several reasoning branches, scoring partial attempts and backtracking, instead of one linear chain. More a research technique than everyday practice.

Role (persona) prompting not in plan

Telling the model who to be ("You are a senior tax accountant"). Helps tone and focus; does not add knowledge the model lacks.

Prompt template not in plan

A prompt with placeholders ({question}, {context}) filled in per request. Kept in version control so changes can be evaluated like code changes.

Delimiters · XML tags not in plan

Marking where each part of a prompt starts and ends, for example <document>...</document> or triple quotes, so the model can tell instructions from data. Also a first, weak line of defence against injection.

Prefilling the response not in plan

Starting the assistant's reply yourself (say with {) so the model continues from there. Forces a format; supported by some APIs and trivially by any engine you control.

Prompt chaining not in plan

Splitting a task into several model calls, each with a focused prompt, where one call's output feeds the next (extract → summarize → translate). Easier to test and debug than one giant prompt.

Prompt engineering · context engineering not in plan

Prompt engineering: crafting instructions and examples to get better outputs. Context engineering: the broader job of deciding everything that goes into the context window (which documents, tool results, memory, history to keep or drop), central for agents.

Prompt optimization · DSPy not in plan

Improving prompts automatically against an eval set instead of by hand. DSPy (Stanford) lets you declare a pipeline's steps and metrics, then searches for prompts and few-shot examples that score best.

Prompt management · versioning not in plan

Storing prompts with versions, owners and eval results, so you know which prompt produced which output and can roll back. Tools: Langfuse, LangSmith, PromptLayer, or simply files in git.

5.2Generation controls and outputs

max_tokens · max_completion_tokens D51

The cap on how many tokens the model may generate. If reached, the response ends with finish_reason: "length" instead of "stop". Reasoning models count their hidden thinking against it.

finish_reason D51

Why generation ended: stop (end token or stop string), length (hit max_tokens), tool_calls (the model wants a tool run), or content_filter.

Logprobs · top_logprobs not in plan

The log-probability the model gave each generated token, and optionally the top alternatives at each position. Used for confidence scores, classification with calibrated probabilities, and checking that two engines agree.

Repetition · presence · frequency penalty not in plan

Sampling adjustments that lower the logits of tokens already used: presence penalty applies once a token has appeared at all, frequency penalty grows with each repeat. They reduce loops and repetition.

min-p sampling not in plan

Keep only tokens whose probability is at least some fraction (say 0.05) of the top token's probability, then sample. Adapts to how confident the model is; popular in local-model tools as an alternative to top-p.

Beam search not in plan

Keep the B most probable partial sequences at every step instead of one, and return the best complete one. Standard in translation; rarely used for chat because it produces bland, repetitive text, and it complicates batching.

Logit bias not in plan

An API parameter that adds a fixed amount to chosen tokens' logits, making them more or less likely, or banning them outright. A crude form of constrained decoding.

Non-determinism · batch invariance D39

Even with temperature 0 and a seed, outputs can differ between runs, because floating-point sums give slightly different results depending on batch size and kernel choice. Batch-invariant kernels guarantee identical results regardless of what else is in the batch.

WhyExplains why your engine and HF may differ by a token after many steps, and why continuous batching can change outputs.

Streaming responses D52

Sending tokens to the user as they are generated rather than after the whole answer. Total time is the same, but users see progress after TTFT instead of waiting for the full response, so it feels much faster.

JSON mode not in plan

An API option guaranteeing the output is valid JSON, but not that it matches any particular shape. Superseded by full structured outputs that follow a schema.

Structured-output libraries: Instructor · Outlines · XGrammar not in plan

Instructor wraps API calls to return validated Pydantic objects, retrying on failure. Outlines and XGrammar do constrained decoding inside the engine (vLLM and SGLang use XGrammar) so output always matches a regex, grammar or JSON Schema.

Grammar-constrained decoding · GBNF not in plan

At each step, mask out every token that would break a formal grammar, so only valid continuations can be sampled. GBNF is llama.cpp's grammar format. The engine-side mechanism behind structured outputs.

Thinking budget · reasoning effort not in plan

A request setting that limits how many tokens a reasoning model may spend thinking (reasoning_effort: low|medium|high, or a token budget). More thinking usually means better answers, higher cost and longer latency.

Test-time compute · inference scaling not in plan

Improving answers by spending more compute at inference (longer reasoning, sampling many answers and picking the best, search) rather than by training a bigger model. A major trend since 2024, and it puts more load on serving systems.

5.3Building LLM applications

AI engineering · AI engineer not in plan

Building products on top of foundation models (prompts, RAG, agents, evals, serving) rather than training models from scratch. Distinct from ML engineering and research; your platform repo is AI engineering, and Forge is the infrastructure underneath it.

Common LLM tasks not in plan

Most production uses fall into a few types: generation (write, rewrite), summarization, extraction (pull fields from text into JSON), classification (label intent or sentiment), question answering over documents (RAG), code generation, and multi-step agents.

Hallucination W22

The model states something false or unsupported, fluently and confidently: invented citations, wrong facts, made-up API functions. Reduced by grounding in retrieved sources, asking for citations, and evals that check faithfulness; never fully eliminated.

Grounding W22

Making answers rely on supplied, checkable sources (retrieved documents, tool results, database rows) rather than the model's memory, ideally with citations pointing to the exact source text.

Conversation memory · chat history not in plan

APIs are stateless: the app must resend earlier messages each turn. When history outgrows the context window, apps truncate old turns, summarize them, or store facts in a database and retrieve them (long-term memory).

Copilot · assistant UX not in plan

Product patterns for LLM features: chat assistants, inline copilots that suggest as you work (code completion), and background automations. Each sets different latency and quality targets (completion needs very low TTFT).

LangChain not in plan

The most widely used framework for chaining prompts, models, retrievers and tools, with integrations for nearly every vendor. Criticized for heavy abstraction; many teams use it for prototypes and write plain code later.

LlamaIndex not in plan

A framework focused on connecting LLMs to your data: document loaders, chunking, indexes, retrievers and query engines for RAG, plus agent support.

Haystack · Semantic Kernel not in plan

Other application frameworks. Haystack (deepset): pipeline-based RAG and search. Semantic Kernel: Microsoft's SDK for C#, Python and Java.

Vercel AI SDK not in plan

A TypeScript library for building streaming chat UIs and tool-calling apps, with one interface across model providers. Common in web front-ends.

Embeddings API not in plan

An endpoint (/v1/embeddings) that turns text into vectors for search, clustering and classification. Hosted options include OpenAI, Cohere, Voyage and Google; open models (BGE, E5, Nomic, Qwen3-Embedding) can be self-hosted.

Latency budget not in plan

How much time a feature can take before users notice or leave (say 300 ms for autocomplete, 2 s to first token for chat). Every step (retrieval, model, tools) must fit inside it.

LLM cost levers W11, W28

The main ways to cut spend: use a smaller model where quality allows (routing), cache repeated requests, shorten prompts, use prompt caching and batch APIs, limit output length, and self-host when volume is high enough.

Serving means running a model and generating tokens. This is Forge itself: the engine in your repo, reached by everything else only through its HTTP API.

6.1Inference core

Prefill D36

The first forward pass, over all prompt tokens at once. Its matmuls have many rows (one per token), so it is usually compute-bound. It fills the KV cache and produces the first output token, so it sets TTFT.

Decode D36

Every later forward pass, each producing one token per sequence. Each step must read every weight from memory to do very little math, so it is memory-bound. Its step time is the per-token latency (TPOT).

KV cache D37–38

Storage for every layer's keys and values for all past tokens, so a decode step only computes K and V for the new token instead of redoing the whole sequence. Size per token = 2 (K and V) × layers × KV heads × head dim × bytes. For Llama 3.2 1B in bf16: 2 × 16 × 8 × 64 × 2 = 32 KiB per token, so a 4,096-token sequence needs 128 MiB.

WhyIt turns generation from quadratic to linear work. Its memory, not compute, limits how many users you can serve at once (section 6.6 and PagedAttention).

Inference arithmetic D36, D45

Back-of-envelope speed limits (from kipply's post). At batch size 1, decode time per token ≈ bytes of weights ÷ memory bandwidth. RTX 4060: 272 GB/s, Llama 3.2 1B ≈ 2.5 GB, so at most about 110 tokens/s. Real numbers come in below that ceiling.

WhyIt tells you how far from the limit you are before you profile anything.

Arithmetic intensity D43–44

FLOPs done per byte moved from memory. A batch-1 decode matmul does 2 FLOPs per 2-byte weight, an intensity of about 1. Batching B sequences reuses each weight B times, raising intensity to about B.

Memory-bound · compute-bound · overhead-bound D43

The three regimes in Horace He's Making Deep Learning Go Brrrr. Time goes to moving bytes, to doing math, or to everything else (Python, kernel launches). Each needs a different fix: fewer bytes (quantization, fusion), better math (tensor cores, tiling) or less overhead (CUDA graphs).

Roofline D44

A chart of attainable FLOPs/s against arithmetic intensity: min(peak FLOPs, intensity × bandwidth). The ridge point (peak ÷ bandwidth) is the intensity where an operation stops being memory-bound. Find your GPU's peak in its spec sheet and plot each kernel on it.

Greedy decoding D33

Always pick the highest-logit token. It's deterministic, which makes it the right mode for correctness tests against HF.

Temperature D39

Divide logits by T before softmax. T < 1 sharpens the distribution (more predictable), T > 1 flattens it (more random), and T → 0 approaches greedy.

Top-k · top-p (nucleus) D39

Top-k: keep only the k most likely tokens. Top-p: keep the smallest set whose probabilities add up to at least p (e.g. 0.9), from The Curious Case of Neural Text Degeneration. Renormalize, then sample. The usual order is temperature → top-k → top-p → sample.

Seed D39, D51

Starting value for the random number generator, so a sampled output can be reproduced. In a batched engine each request needs its own generator.

Stop conditions D40

When to end a sequence: an EOS token, max_tokens reached (finish_reason: "length"), or a user-supplied stop string (finish_reason: "stop").

Incremental detokenization D40

Turning token IDs into text as they arrive. One character can span several tokens (emoji, non-Latin scripts) and tokenizers merge spaces, so you decode a sliding window and only emit text once it is stable. HF's TextStreamer shows the pattern.

6.2GPU hardware

SM (streaming multiprocessor) D64, D66

The GPU's building block: a cluster of cores, tensor cores, registers and shared memory. Your RTX 4060 has 24 SMs. Each thread block runs entirely on one SM.

Thread · block · grid D65

CUDA's hierarchy. A kernel launches a grid of blocks; each block is up to 1,024 threads that can share memory and synchronize. Each thread uses its block and thread index to decide which data to handle.

Warp D65–66

32 threads that execute the same instruction together. If threads in a warp take different branches (divergence), the branches run one after the other.

Global memory · HBM · GDDR D66

The GPU's main memory (VRAM). Datacenter GPUs use stacked HBM (H100: ~3.35 TB/s); your 4060 uses GDDR6 (272 GB/s). Every decode step streams all the weights out of it.

Shared memory · SRAM · L1 D66

Small on-chip memory per SM (about 100 KB), around an order of magnitude faster than global memory. A kernel controls it explicitly to hold tiles it will reuse.

WhyFlashAttention exists to keep attention's intermediate values here instead of writing them to global memory.

Registers · L2 cache D66

Registers: per-thread storage, fastest of all. L2: a cache shared by all SMs (24 MB on the 4060) that catches repeated reads from global memory.

Memory coalescing D67

When the 32 threads of a warp read 32 consecutive addresses, the hardware merges them into a few wide transactions. Scattered addresses mean many transactions and a fraction of the bandwidth.

Tensor cores D66, D88

Units that do a small matrix multiply-accumulate (e.g. a 16×16 tile) in one instruction. They supply most of a GPU's FLOPs, but only for low-precision inputs (bf16, fp16, fp8, int8). Your 4060 (Ada) has 4th-generation tensor cores with FP8 support.

Occupancy D67

How many warps are active on an SM compared with the maximum. More warps let the SM switch to another warp while one waits on memory. Limited by registers and shared memory used per block.

Kernel · kernel launch overhead D46, D59

A kernel is a function that runs on the GPU. Launching one costs several microseconds of CPU time. A small model's decode step launches hundreds of kernels, so launch time can exceed GPU time.

Asynchronous execution · synchronize D46

The CPU queues kernels and moves on; the GPU runs them later. Timing GPU work without torch.cuda.synchronize() or CUDA events measures only how long it took to queue the work.

Compute capability · Ada · Hopper · Ampere D64, D87

NVIDIA GPU generations: Ampere (A100, sm_80), Ada (RTX 40 series, sm_89, your card), Hopper (H100, sm_90), Blackwell (B200, sm_100). The compute capability number decides which instructions and data types a kernel can use.

TMA · warp specialization D87

Hopper features. TMA (Tensor Memory Accelerator) is a hardware unit that copies whole tiles between global and shared memory asynchronously. Warp specialization dedicates some warps to loading data while others compute. FlashAttention-3 depends on both.

Modal GPU Glossary · GPU MODE D64

Two learning resources. Modal's glossary defines every GPU term with diagrams. GPU MODE is a community with lecture videos and a repo on CUDA, Triton and performance.

6.3Kernels and Triton

CUDA D65–69

NVIDIA's C++ programming model for GPUs: you write the code one thread runs and launch it over a grid. Maximum control, maximum effort.

torch.utils.cpp_extension · load_inline D68–69

Compile CUDA or C++ code from inside Python and call it as a PyTorch op. It's how you run your first hand-written CUDA kernels against tensors.

Triton D71–76

A Python language and compiler for GPU kernels. You write what one program instance does to a whole block of data (tl.load a tile, compute, tl.store), and the compiler handles threads, coalescing and shared memory. tl.program_id says which block you are; a mask guards the ragged edge.

WhyForge's custom kernels are written in Triton, and Triton is also what torch.compile generates.

Kernel fusion D72, D74–75

Combining several operations into one kernel so intermediate results stay in registers or shared memory instead of making round trips to global memory. For memory-bound ops like RMSNorm, the speed-up is roughly the number of bytes saved.

Tiling D73, D88

Splitting a big matmul into tiles that fit in shared memory, so each loaded tile is reused many times before the next load. This is how matmuls get high arithmetic intensity.

GEMM · GEMV D73, D88

General matrix-matrix multiply and matrix-vector multiply. Prefill is GEMM. Batch-1 decode is effectively GEMV, which can't keep tensor cores busy.

Autotuning D73

@triton.autotune benchmarks several configurations (block sizes, number of warps, pipeline stages) and keeps the fastest for each input shape.

triton.testing.do_bench D86

Triton's benchmarking helper. It warms up, clears the L2 cache, repeats the run and returns a robust timing. Use it for every kernel number in RESULTS.md.

cuBLAS D73, D88

NVIDIA's tuned linear-algebra library and what torch.matmul calls. It's the bar to compare your matmul against; matching 70–90% of it in Triton is a good result.

CUTLASS not in plan

NVIDIA's C++ template library for building custom GEMMs and attention kernels. FlashAttention-3 and many production kernels are built on it.

Liger Kernel D74–75

An open-source collection of Triton kernels for LLM layers (RMSNorm, SwiGLU, RoPE, cross-entropy). Read it after writing your own versions.

torch.testing.assert_close D30 onward

Compares two tensors within a relative and absolute tolerance. bf16 has only about 3 significant digits, so tolerances near rtol≈1.6e-2 are normal. This is the backbone of every Forge correctness test.

6.4Attention kernels

SDPA (scaled_dot_product_attention) D31, D86

PyTorch's built-in attention op. It picks a FlashAttention, memory-efficient or plain math backend automatically. It's your correctness reference and the speed baseline your kernels must beat or match.

Online softmax D78

Computes softmax in one pass over the data by keeping a running maximum m and running sum l. When a larger value appears, the sum so far is rescaled by exp(m_old − m_new). From Milakov & Gimelshein (2018).

WhyIt lets attention process keys block by block without ever seeing the whole row, which is the core of FlashAttention.

FlashAttention D79

An exact attention algorithm that tiles Q, K and V into shared memory and uses online softmax, so the N × N score matrix is never written to global memory. Memory drops from O(N²) to O(N) and speed rises because far fewer bytes move. It is "IO-aware": designed around memory traffic, not FLOPs.

FlashAttention-2 D80

A rework of the same idea: parallelizes across the sequence as well as batch and heads, swaps the loop order so each block of queries stays put, and cuts non-matmul work. About 2× faster than v1.

FlashAttention-3 D87

Hopper-specific: overlaps data movement (TMA) with compute through warp specialization and supports FP8. It won't run on your 4060, but you need to be able to explain it.

Fused attention (Triton tutorial) D81

Triton's official FlashAttention-style tutorial kernel. Read it line by line before writing your own prefill kernel.

Prefill attention kernel D82

Attention where many queries attend to many keys with a causal mask. Tiles entirely above the diagonal are skipped, so causal attention costs about half of full attention.

Decode attention · Flash-Decoding D83, D85

In decode each sequence has one query, so parallelizing over queries leaves most SMs idle. Flash-Decoding splits the long KV sequence into chunks processed in parallel (split-K), then combines the partial results using their saved max and sum values.

Split-K · reduction D83

Splitting the summed-over dimension (here, the keys) across blocks, then adding the partial results in a second small step. A general GPU trick for when the output alone is too small to fill the GPU.

6.5Speed-ups and profiling

gpt-fast D57

The PyTorch team's ~1,000-line Llama inference demo: static KV cache, torch.compile, int8/int4 weights, speculative decoding and tensor parallelism. It's your template for the "quick speed-ups" week.

torch.compile D58

Captures your Python model into a graph (TorchDynamo) and generates fused Triton kernels (Inductor). mode="reduce-overhead" also adds CUDA graphs. A graph break is a spot it can't capture; recompiles happen when shapes change.

Static KV cache D57–60

A KV cache allocated once at maximum size and never resized, so tensor addresses and shapes never change. Both torch.compile and CUDA graphs need this.

CUDA graphs D59–60

Record a whole sequence of kernel launches once, then replay all of it with a single launch. This removes per-kernel CPU overhead, which is often the biggest cost in small-model decode. The catch: shapes and memory addresses must be identical on replay, so you capture one graph per batch-size bucket and copy inputs into fixed buffers.

PyTorch profiler D46

torch.profiler records CPU ops and GPU kernels with timings. It prints a table of the most expensive ops and can export a trace for Perfetto.

Nsight Systems (nsys) · NVTX D47

NVIDIA's whole-system timeline: CPU threads, CUDA API calls, kernels and memory copies on one time axis. Gaps where the GPU is idle are overhead. NVTX ranges are labels you add in code so the timeline shows "prefill", "decode step" and so on.

Nsight Compute (ncu) not in plan

NVIDIA's per-kernel profiler: achieved bandwidth, occupancy, cache hit rates and a roofline for one kernel. It's the next tool when a Triton kernel is slower than expected.

Perfetto D46

A browser-based trace viewer (ui.perfetto.dev). Open PyTorch profiler traces in it to see kernels on a timeline.

6.6Serving many users

Batching D92

Running several sequences through one forward pass. Weights are read from memory once and used for all of them, so decode throughput grows almost linearly with batch size until compute or KV memory runs out.

Static batching D94

Collect a batch, run it until every sequence finishes, then start the next. Short requests sit idle waiting for the longest, and new arrivals wait for the whole batch.

Continuous batching · iteration-level scheduling D92–97

Re-decide the batch at every decode step: finished sequences leave immediately and waiting ones join. Introduced by the Orca paper (OSDI 2022). This is the single biggest throughput gain in serving.

Orca · selective batching D93

Orca's companion idea: sequences of different lengths can't share one attention call, but their linear layers can. So all tokens are flattened into one matmul for the linear layers, and attention runs per sequence.

Scheduler loop · request lifecycle D95–96

The engine's main loop: admit waiting requests if memory allows, run one step, send each new token to its stream, free finished sequences, repeat. A request moves through WAITING → RUNNING → (PREEMPTED) → FINISHED. Design doc 2 covers this.

Padding · packed (varlen) prefill · cu_seqlens D109

Padding extends every prompt to the longest one, wasting compute. Packed prefill concatenates all prompts into one flat token tensor and passes cu_seqlens (cumulative sequence lengths, e.g. [0, 7, 19, 24]) so attention knows where each sequence starts and ends.

KV cache fragmentation D99

Reserving one contiguous max-length KV region per request wastes memory on space reserved but unused (internal fragmentation) and on gaps between regions (external fragmentation). The PagedAttention paper measured 60–80% waste in earlier systems.

PagedAttention D99–106

vLLM's KV cache design (SOSP 2023). The cache is a pool of fixed-size blocks (e.g. 16 tokens each). Each sequence has a block table listing which physical blocks hold its logical blocks, in order. Blocks are allocated as the sequence grows and freed when it finishes, so waste drops to under 4% and more sequences fit.

Block allocator · reference counts D102

Manages the free list of physical blocks. Each block has a reference count (how many sequences point at it), so blocks can be shared, for example by prefix caching, and are freed only when the count reaches zero.

Block table · slot mapping D102–103

The block table is a per-sequence list of physical block IDs. The slot mapping says where a new token's K and V are written: slot = block_id × block_size + offset_in_block.

Paged decode attention kernel D104

A decode attention kernel that looks up each key and value block through the block table instead of assuming one contiguous array.

Copy-on-write D100

Sequences that share blocks (e.g. several samples from one prompt) read the same physical block until one of them needs to write to it. Only then is it copied.

Preemption · recompute · swap D107–108

When KV memory runs out mid-generation, the scheduler evicts a running sequence. Recompute drops its KV cache and re-prefills later. Swap copies its KV to CPU memory and back. Recompute is simpler and usually what engines do now.

Prefix caching D113–116

Keeping KV blocks from finished requests so a new request with the same starting tokens (system prompt, chat history, few-shot examples) reuses them instead of recomputing. That skips prefill for the shared part and cuts TTFT.

Hash-based prefix caching D114–115

vLLM's approach: each full block gets a key of hash(parent block's hash, this block's token IDs), so equal keys mean equal prefixes. A hash → block table finds hits. Unused cached blocks are evicted least-recently-used (LRU) when memory is needed.

RadixAttention D113

SGLang's approach: a radix tree (a compressed tree of token sequences) whose paths map to KV cache entries. Finds the longest matching prefix and evicts least-recently-used leaves.

Chunked prefill · token budget D117–118

Splitting a long prompt's prefill into chunks (e.g. 512 tokens) and mixing one chunk with ongoing decode tokens in each step, under a per-step token budget. From Sarathi-Serve. Running decodes no longer freeze behind one huge prompt, so TPOT stays smooth.

Head-of-line blocking D117

When one big item at the front of a queue holds up everything behind it. A long prefill blocking decodes is the classic case in LLM serving.

Backpressure · admission control D122

Under overload, refuse or delay new work (HTTP 429, a bounded queue) instead of accepting everything and letting latency grow without limit. Admission control is the rule that decides what gets in.

Cancellation D52, D122

When a client disconnects mid-stream, abort its request and free its KV blocks right away. Otherwise the GPU keeps generating text nobody will read.

Load test · stress test · Poisson arrivals D120, D123

A load test sends realistic traffic, usually Poisson arrivals (random, independent arrival times at an average rate), and measures latency. A stress test pushes edge cases on purpose: memory exhaustion, mass disconnects, very long prompts.

nano-vllm D101

A ~1,200-line reimplementation of vLLM's core (scheduler, paged KV cache, prefix caching, CUDA graphs). Read it to see the whole design at once before building yours.

6.7Speculative decoding

Speculative decoding D127

A cheap draft proposes the next k tokens; the big target model checks all k in one forward pass and keeps the longest correct prefix plus one token of its own. Decode is memory-bound, so checking k tokens costs about the same as generating one.

Draft model · target model D127, D131

The small, fast proposer (e.g. Llama 3.2 1B) and the large model whose output you actually want (e.g. Llama 3.1 8B). They must share a tokenizer.

Speculative sampling · rejection sampling D128, D130

The sampling version (Leviathan et al., Chen et al., 2023). Accept a drafted token x with probability min(1, p(x)/q(x)), where p is the target's probability and q the draft's. On rejection, sample from the normalized max(0, p − q). The output distribution is provably exactly the target's.

Greedy speculative decoding D129

The simple case: accept drafted tokens while they equal the target's argmax. The output is identical to plain greedy decoding, which makes testing easy.

Acceptance rate (α) D131

The chance that a drafted token is accepted. Expected tokens per target pass = (1 − α^(k+1)) / (1 − α). With α = 0.8 and k = 4 that's about 3.4 tokens per pass.

Chi-square test D130

A statistical test (scipy.stats.chisquare) of whether observed counts match expected probabilities. Use it to show that your speculative sampler's outputs follow the target's distribution.

Medusa D132

Adds extra prediction heads to the target model that guess tokens +2, +3 and so on in parallel. A tree of candidates is checked in one pass with "tree attention". No separate draft model.

EAGLE D132

A small draft head that predicts from the target's own hidden states (features), not just tokens. It gets higher acceptance rates than a separate small model; EAGLE-3 is the current version used in vLLM and SGLang.

Prompt lookup decoding · n-gram drafting D132

The draft is copied from the prompt: find the last few generated tokens earlier in the context and propose what followed them there. It costs nothing and works well for summarization, RAG answers and code edits.

Assisted generation D132

Hugging Face's name for speculative decoding (assistant_model= in generate). It's a working reference to compare against.

6.8Quantization

Quantization D134

Storing numbers in fewer bits: x ≈ scale × (q − zero_point), where q is a small integer. Smaller weights mean fewer bytes per decode step, so a memory-bound engine gets faster, and bigger models fit.

Scale · zero point · symmetric/asymmetric D134, D136

The scale maps the integer range onto the real range; the zero point shifts it. Symmetric quantization has zero point 0 (range centred on 0); asymmetric allows an offset.

Per-tensor · per-channel · per-group D136–138

How many scales you keep: one per tensor, one per output channel (row), or one per group of e.g. 128 values. Finer granularity gives better accuracy for a little extra memory. 4-bit needs per-group.

Weight-only quantization (W8A16, W4A16) D136, D138

Weights stored in 8 or 4 bits and converted back to bf16 inside the matmul kernel; activations stay bf16. It targets exactly the decode bottleneck, reading weights.

W8A8 · activation quantization D135

Weights and activations both int8, so the matmul runs on int8 tensor cores. It helps compute-bound prefill, but activations are much harder to quantize than weights.

Outliers D135

A few activation channels with values 100× larger than the rest. One scale per tensor then crushes all the small values to zero. This is the central problem activation quantization papers solve.

LLM.int8() D135

Splits each matmul: the few outlier columns run in fp16, everything else in int8. Accurate, but the split costs speed.

SmoothQuant D135

Moves the difficulty from activations to weights with a per-channel factor s: X·W = (X/s)·(s·W). Both sides become easy to quantize, which makes W8A8 practical.

GPTQ D137

One-shot post-training weight quantization. It quantizes one column at a time and adjusts the remaining columns to compensate for the error, using second-order (Hessian) information from a small calibration set. Strong 4-bit results.

AWQ (activation-aware weight quantization) D137

Observes that about 1% of weight channels matter most: the ones meeting large activations. It scales those up before quantizing so they keep precision. Simple, needs no backprop, and is widely used for 4-bit models.

Calibration data D137

A few hundred sample texts run through the model to measure activation statistics for GPTQ, AWQ or SmoothQuant. If it doesn't resemble real traffic, quality suffers.

Int4 packing · dequantizing matmul D138

Two 4-bit values packed into each byte. The kernel loads packed weights, unpacks them, applies scales and multiplies, all in registers. Memory traffic falls by 4× compared with bf16.

FP8 (E4M3, E5M2) D139

8-bit floating point. E4M3 (4 exponent, 3 mantissa bits) has more precision and is used for weights and activations; E5M2 has more range. Supported by tensor cores on Ada (your 4060) and Hopper.

Quality-versus-speed table D139

One table: format × tokens/s × memory × perplexity. Every quantization claim you make should point to a row in it.

FP8 KV cache · NVFP4/MXFP4 · GGUF not in plan

Quantizing the KV cache itself (doubles how many tokens fit); Blackwell's 4-bit "microscaling" formats with a shared scale per small block; and llama.cpp's GGUF file format with its own "k-quant" schemes.

6.9Multi-GPU and disaggregation

Tensor parallelism (TP) D141–146

Splitting each weight matrix across GPUs so each computes a slice of every layer, then combining results with a collective. It cuts per-GPU memory and per-token latency, but adds communication every layer.

Megatron-LM · column/row parallel D141, D144

The 2019 NVIDIA paper defining the standard split. Column-parallel splits a matrix's outputs (each GPU gets whole output features, no communication). Row-parallel splits its inputs (each GPU gets a partial sum, then an all-reduce). Llama: gate/up column-parallel, down row-parallel; attention split by heads. That's two all-reduces per layer.

Collectives: all-reduce · all-gather · reduce-scatter · broadcast D142

Group communication ops. All-reduce: every GPU ends up with the sum of everyone's tensors. All-gather: every GPU ends up with everyone's pieces concatenated. Reduce-scatter: sum, then each GPU keeps one slice. Broadcast: one GPU sends to all.

NCCL D142–143

NVIDIA's collective communication library ("nickel"). torch.distributed uses it for GPU tensors.

torch.distributed · rank · world size · torchrun D143

PyTorch's multi-process API. Each GPU gets one process with a rank (0, 1, …) out of world size processes. torchrun launches them and sets the environment so they can find each other.

NVLink · PCIe D145–146

GPU-to-GPU links. NVLink is a direct high-bandwidth bridge; PCIe goes through the motherboard and is far slower. Tensor parallelism's cost depends mostly on which one your rented pair has, so record it.

Data parallelism · replicas not in plan

A full copy of the model on each GPU, each serving different requests. The simplest way to scale serving when the model fits on one GPU.

Pipeline parallelism · expert parallelism not in plan

Pipeline: different layers on different GPUs, with requests flowing through like an assembly line. Expert: in MoE models, different experts on different GPUs.

Disaggregated prefill/decode D148–152

Running prefill and decode on separate GPU pools and sending the KV cache from one to the other. Prefill bursts no longer disturb decode latency, and each pool can be sized and tuned on its own.

DistServe · Splitwise D148–149

The two papers behind disaggregation. DistServe optimizes goodput under TTFT and TPOT targets. Splitwise (Microsoft) splits the phases across machines and shows each phase can even use different GPU types.

KV transfer D151

Moving a sequence's KV blocks from the prefill worker to the decode worker. Its size and speed decide whether disaggregation pays off.

6.10Server and API

OpenAI-compatible API D50–52

The de facto standard HTTP interface for LLMs. POST /v1/chat/completions takes model, messages, max_tokens, temperature, top_p, stream, seed. It returns choices[].message, a finish_reason (stop or length) and usage (token counts).

WhyIt's the only boundary between Forge and the rest of the platform (architecture rule 1). Any OpenAI client, gateway or eval harness works with Forge unchanged.

/v1/models D51

Lists the models a server offers. Clients and gateways use it for discovery and health checks.

FastAPI · pydantic · uvicorn D50

FastAPI is an async Python web framework. pydantic models define and validate request and response bodies. uvicorn is the ASGI server that runs the app.

asyncio · event loop D50

Python's single-threaded concurrency: one event loop switches between many coroutines whenever one awaits. Any blocking call, like a GPU forward pass, freezes every request, so the engine must run in its own thread or process.

to_thread · run_in_executor D50

Ways to run blocking work in a thread pool from async code without blocking the event loop.

Engine / API separation D96

The engine loop owns the GPU in its own thread or process; the API layer only puts requests on a queue and reads results from per-request output queues. vLLM runs its engine core in a separate process for the same reason.

Server-sent events (SSE) D52

A simple HTTP streaming format: the response stays open and sends lines like data: {json} followed by a blank line. OpenAI streams chat.completion.chunk objects with a delta and ends with data: [DONE].

openai-python D51–52

The official client. Point it at Forge with base_url="http://localhost:8000/v1"; if it works unchanged, your API is compatible.

traceparent · W3C Trace Context D51, W43

A standard HTTP header that carries the ID of the trace a request belongs to: 00-<32-hex trace id>-<16-hex parent span id>-<flags>. Forge reads it so its work joins the gateway's trace (architecture rule 2).

/metrics D121

An HTTP endpoint exposing counters and histograms in Prometheus's text format: queue length, KV usage, prefix hit rate, TTFT and TPOT. See part 11.

6.11Metrics and benchmarks

TTFT (time to first token) D48, D53

From request arrival to the first streamed token. It's queue wait plus prefill, and it's what makes a chat feel responsive.

TPOT (time per output token) D48, D53

Average gap between tokens after the first: (end-to-end latency − TTFT) ÷ (output tokens − 1). Sets reading speed; under ~50 ms feels faster than reading.

ITL (inter-token latency) not in plan

Every individual gap between tokens, not just the average. Shows stalls that TPOT hides, such as decode pausing behind a long prefill.

End-to-end latency D48

From request arrival to the last token.

Throughput D48, D53

Output tokens per second summed over all requests (also requests per second). Rises with batching while per-request latency gets worse: the central trade-off of serving.

Percentiles: p50 · p90 · p99 D53

The value below which 50%, 90% or 99% of measurements fall. p99 is the "tail": one in a hundred users sees at least that. Report percentiles, never just the mean.

SLO · goodput D148

An SLO (service-level objective) is a target such as "p99 TTFT < 500 ms". Goodput is the request rate served while meeting the SLOs. It's a more honest number than raw throughput.

Concurrency vs request rate D53, D120

Closed-loop: keep K requests in flight (send a new one when one finishes). Open-loop: send at a fixed arrival rate regardless of how fast you respond. Open-loop shows queueing collapse; closed-loop hides it.

Latency–throughput curve D53, D124

Latency plotted against load. It stays flat, then rises sharply at the "knee" where the server saturates. Comparing engines means comparing these curves, not single points.

ShareGPT D120, D124, D155

A dataset of real ChatGPT conversations, the standard source of realistic prompt and output lengths for serving benchmarks.

vLLM benchmark scripts D53

vLLM's serving benchmark (in benchmarks/, also vllm bench serve). Copy its definitions so your numbers are comparable.

Benchmark matrix D155

The grid you test: model × hardware × workload × engine × setting. Fixing it in advance stops you cherry-picking results.

WikiText · lm-evaluation-harness · MMLU · GSM8K D136, D139, D157

WikiText-2: the standard text for perplexity. lm-evaluation-harness: EleutherAI's tool that runs standard task benchmarks against a model or an API endpoint. MMLU: multiple-choice knowledge across 57 subjects. GSM8K: grade-school maths word problems.

Warm-up · variance not in plan

The first runs include compilation, memory allocation and GPU clock ramp-up, so discard them. Repeat runs and report the median. Thermal throttling on a laptop or small card can move numbers by 10%.

vLLM D54, D124, D156

The most widely used open-source serving engine, where PagedAttention came from. Forge's benchmark target and a target for your open-source PR.

SGLang D113, D156

A fast open-source engine from the LMSYS group: RadixAttention, a low-overhead scheduler and fast structured output. The other benchmark target.

TensorRT-LLM not in plan

NVIDIA's engine: builds optimized engines ahead of time with NVIDIA's own kernels. Often fastest on NVIDIA hardware, harder to modify.

TGI not in plan

Hugging Face's Text Generation Inference server, an early continuous-batching engine.

llama.cpp · Ollama not in plan

LMCache · NVIDIA Dynamo · llm-d not in plan

6.13More serving techniques

FlashInfer not in plan

A library of attention and sampling kernels built for serving engines: paged and ragged KV layouts, cascade attention for shared prefixes, and fast top-k/top-p sampling. vLLM and SGLang can use it as their attention backend.

Attention backend not in plan

The pluggable component in an engine that runs attention over the paged KV cache: FlashAttention, FlashInfer, Triton kernels or vendor libraries. Engines pick one per GPU type and feature set.

Multi-LoRA serving · S-LoRA · Punica D171

Serving many LoRA fine-tunes of one base model on the same GPU, with requests for different adapters batched together. Special kernels (Punica's SGMV, S-LoRA) apply each request's small adapter while sharing the big base matmul.

WhyLets one deployment serve hundreds of customer fine-tunes cheaply.

KV cache offloading · tiered KV cache not in plan

Moving KV blocks that are not needed right now from GPU memory to CPU memory or SSD, and bringing them back on a prefix hit instead of recomputing them. Turns prefix caching into a much bigger, cheaper cache.

Overlap scheduling not in plan

Preparing the next batch on the CPU (scheduling, building block tables) while the GPU is still running the current step, so the GPU never waits. SGLang and vLLM's newer engine both do this.

Priority · fairness scheduling not in plan

Scheduling policies beyond first-come-first-served: request priorities, per-user fair share, or shortest-job-first, to protect interactive traffic or paying tenants when the engine is overloaded.

Wide expert parallelism · DeepEP not in plan

Serving a large MoE model by spreading its experts across many GPUs and sending each token to the GPUs holding its chosen experts (all-to-all communication). DeepEP is DeepSeek's library for that communication.

Triton Inference Server not in plan

NVIDIA's general model server (not related to the Triton kernel language), which hosts models from many frameworks with dynamic batching and model management; it can run TensorRT-LLM as a backend. Now part of NVIDIA Dynamo's ecosystem.

Dynamic batching (classic serving) not in plan

The pre-LLM batching approach of general model servers: wait a few milliseconds to collect requests into one batch, run it, return all results. Fine for fixed-size inputs; wasteful for generation, which is why continuous batching exists.

TEI · embedding and reranker serving not in plan

Serving embedding and reranker models is a different problem from generation: one forward pass per request, no decode loop, no KV cache. Hugging Face's Text Embeddings Inference (TEI) and Infinity are dedicated servers; vLLM can also serve embeddings.

LMDeploy · MLC LLM · ExecuTorch not in plan

More engines. LMDeploy: Shanghai AI Lab's fast serving engine. MLC LLM: compiles models to run on phones, browsers (WebGPU) and many GPUs. ExecuTorch: PyTorch's runtime for on-device models.

On-device inference not in plan

Running models on phones and laptops (Apple Intelligence, Gemini Nano, llama.cpp, MLX). Limited by memory size and bandwidth even more than your 4060, so small, heavily quantized models dominate.

07RAG and retrieval

Retrieval-augmented generation: find the passages relevant to a question and put them in the prompt, so the model answers from your documents rather than from memory. Lives in rag/, W3–4, W20–22, W39–40.

7.1Ingestion

Corpus · document set W3

The collection you search. Your plan suggests public company annual reports (e.g. US 10-K filings), which have long PDFs, tables and lots of numbers, a realistic hard case.

Parsing W3

Turning PDFs and HTML into clean text with structure (headings, tables, page numbers). Bad parsing caps everything downstream. Tools include PyMuPDF, pdfplumber, unstructured and Docling.

Chunking · chunk size · overlap W3–4

Splitting documents into passages to embed and retrieve. Fixed-size chunks are N tokens each; structure-aware chunks follow headings and paragraphs. Overlap repeats a few sentences between chunks so facts on a boundary aren't cut in half. Small chunks are precise but lack context; large chunks carry context but blur the embedding.

Embedding model W3

A model that maps text to a fixed-length vector (e.g. 384–1,024 numbers) so texts with similar meaning land close together. Small open models (bge, e5, gte, nomic-embed families) run fine on your 4060.

Cosine similarity W3

The cosine of the angle between two vectors, from −1 to 1. With vectors normalized to length 1 it's just the dot product. The usual "closeness" score for embeddings.

Incremental updates · content hash W20

Re-processing only new or changed documents. A hash of each document's content tells you whether it changed since the last run.

Deduplication W20

Removing repeated content: exact duplicates by hash, near-duplicates by similarity (e.g. MinHash). Duplicates waste index space and crowd out other results in top-k.

Freshness W20

How far the index lags behind the source documents. Measure it as the time from a document changing to its new chunks being searchable.

Lineage W20

A record of what produced what: document version → parser version → chunk → embedding model version. It lets you answer "why did it retrieve that?" and re-run exactly the affected part.

Re-embedding · embedding versioning W40

When you change the embedding model, every vector must be recomputed, because vectors from different models aren't comparable. Store the model version with each vector.

Metadata not in plan

Fields stored with each chunk (company, year, section, page) so a search can be filtered, e.g. only 2024 filings, before ranking.

7.2Documents and chunking

Document loaders W3

Code that reads sources (PDFs, web pages, Word files, Notion, Confluence, Slack) into plain text plus metadata. Every framework ships dozens; most quality problems in RAG start here.

PDF parsing · OCR W3

PDFs store positioned characters, not paragraphs, so extracting clean text in reading order is hard. Scanned PDFs are images and need OCR (optical character recognition). Tables, columns and headers often come out scrambled.

Layout-aware parsers: Unstructured · Docling · LlamaParse not in plan

Tools that detect a document's structure (headings, tables, lists, figures) before extracting text, often using vision models. Docling (IBM, open source), Unstructured and LlamaParse are common choices.

Recursive character splitter W3

The default chunking method: split on paragraphs, then sentences, then words, until each piece fits the chunk size, with some overlap between neighbouring chunks.

Structure-aware chunking not in plan

Splitting along the document's own structure (Markdown headings, HTML sections, code functions) so each chunk is a coherent unit, and storing the heading path ("Guide › Install › Linux") with it.

Semantic chunking not in plan

Placing chunk boundaries where the topic changes, detected by a drop in embedding similarity between consecutive sentences.

Parent–child (small-to-big) retrieval not in plan

Search over small, precise chunks, but put their larger parent section into the prompt so the model gets enough surrounding context.

Contextual retrieval not in plan

Before embedding each chunk, have an LLM write one or two sentences placing it in its document ("This section is from Acme's 2024 annual report, about revenue") and prepend them. Anthropic reported large drops in retrieval failures; prompt caching keeps the cost down.

Late chunking not in plan

Run a long-context embedding model over the whole document first, then pool token vectors into chunk vectors, so each chunk's embedding reflects the document around it.

Multimodal RAG · ColPali not in plan

Retrieving images, slides and scanned pages as well as text. ColPali embeds page images directly with a vision-language model, skipping text extraction entirely.

Document-level access control W45

Making sure retrieval only returns chunks the asking user is allowed to see, by storing permissions as metadata and filtering every search. Leaking another tenant's document through RAG is a serious bug.

7.3Retrieval

Vector search · top-k W3

Embed the question, find the k chunks whose vectors are closest. For a few thousand chunks an exact scan (numpy, FAISS "flat") is fast enough.

ANN · HNSW not in plan

Approximate nearest neighbour search trades a little recall for big speed at scale. HNSW (hierarchical navigable small world) is the most common ANN index: a layered graph you walk greedily toward the query. Becomes relevant at W39's 10× scale.

Vector database not in plan

Storage plus an index for vectors. FAISS is a library; pgvector adds vectors to Postgres; Qdrant, Chroma and LanceDB are dedicated stores. pgvector or FAISS is plenty for this project.

BM25 · keyword search W21

The classic text-ranking formula: scores a passage by how often query words appear in it, weighted up for rare words and adjusted for passage length. It beats embeddings on exact names, ticker symbols, codes and numbers, which are common in financial reports.

Hybrid search · reciprocal rank fusion W21

Run keyword and vector search and merge the two ranked lists. Reciprocal rank fusion (RRF) is the usual merge: each result scores Σ 1/(60 + rank) over the lists it appears in.

Reranker · cross-encoder · bi-encoder W21

An embedding model is a bi-encoder: question and passage are encoded separately, which is fast. A cross-encoder reads question and passage together and outputs one relevance score, which is slower but far more accurate. The pattern: retrieve 50 cheaply, rerank to the best 5.

Query rewriting · HyDE W40

Using an LLM to improve the question before searching: expand acronyms, resolve "it" from chat history, split multi-part questions. HyDE (hypothetical document embeddings) has the LLM write a fake answer and searches with that instead.

Context window · lost in the middle not in plan

The maximum tokens a model can take. Models also use information at the start and end of a long prompt better than the middle, so put the best passages first.

7.4Embeddings and vector indexes

Dense vs sparse retrieval W21

Dense: embed text as a vector of a few hundred to a few thousand real numbers and compare meanings. Sparse: represent text as weights over vocabulary words, mostly zero, and match words (BM25). Dense handles paraphrase; sparse handles exact names, codes and rare terms. Hybrid uses both.

SPLADE · learned sparse retrieval not in plan

A model that outputs sparse word weights, including related words that do not appear in the text, so you get keyword-index speed with some semantic matching.

Distance metrics: cosine · dot product · L2 W3

Ways to compare vectors. Cosine similarity compares direction only; dot product also rewards length; L2 (Euclidean) distance is straight-line distance. For normalized vectors all three give the same ranking. Use the one your embedding model was trained with.

Embedding dimension · Matryoshka embeddings not in plan

The vector length (384, 768, 1,536, 3,072...). Bigger is usually better but costs storage and search time. Matryoshka-trained models front-load information so you can truncate vectors (3,072 → 256) with little loss.

Embedding quantization not in plan

Storing vectors in int8 or even 1 bit per dimension (binary) instead of float32, shrinking indexes 4–32×, then rescoring the top results with full-precision vectors.

MTEB not in plan

The Massive Text Embedding Benchmark: a leaderboard of embedding models across retrieval, clustering, classification and many languages. The usual place to shortlist an embedding model.

Embedding models: BGE · E5 · GTE · Nomic · text-embedding-3 · Voyage · Cohere W3

Common choices. Open: BGE (BAAI), E5 (Microsoft), GTE and Qwen3-Embedding (Alibaba), Nomic, Jina. Hosted: OpenAI text-embedding-3, Voyage, Cohere Embed, Google's Gemini embeddings.

Flat (exact) index W3

Comparing the query against every stored vector. Perfect recall, fine up to perhaps a million vectors, and the baseline that approximate indexes are measured against.

IVF (inverted file index) not in plan

An approximate index that clusters vectors with k-means and, at query time, searches only the few clusters nearest the query (nprobe of them). More clusters probed means better recall and slower search.

Product quantization (PQ) not in plan

Compressing each vector by splitting it into pieces and replacing each piece with the ID of its nearest stored "centroid". Vectors shrink to a few bytes and distances are estimated from lookup tables. Often combined with IVF (IVF-PQ).

HNSW parameters: M · ef_construction · ef_search not in plan

HNSW builds a layered graph linking each vector to its neighbours and searches it greedily. M is links per node (memory and recall), ef_construction is build-time effort, ef_search is query-time effort, the main dial between recall and latency.

FAISS not in plan

Meta's library of vector indexes (flat, IVF, PQ, HNSW, with GPU versions). Not a database: no persistence or filtering of its own, but the engine many databases build on.

pgvector not in plan

A PostgreSQL extension adding a vector column type and HNSW/IVF indexes, so embeddings live next to your ordinary tables and SQL filters. Often the simplest production choice.

Vector databases: Qdrant · Weaviate · Milvus · Pinecone · Chroma · LanceDB not in plan

Dedicated vector stores adding persistence, metadata filtering, hybrid search, replication and multi-tenancy on top of ANN indexes. Pinecone is hosted-only; the rest are open source with hosted options. Chroma and LanceDB are lightweight and embeddable.

Elasticsearch · OpenSearch · Vespa not in plan

Established search engines that do BM25 keyword search at scale and have added vector search, making them natural hybrid-search platforms.

Metadata filtering · pre- vs post-filtering not in plan

Restricting search by fields such as date, source or tenant. Pre-filtering applies the filter during the ANN search (accurate, harder to make fast); post-filtering searches first and drops non-matching results, which can leave too few.

7.5Advanced retrieval patterns

Multi-query · query expansion W40

Have an LLM write several rephrasings of the question (or add synonyms), retrieve for each, and merge the results with RRF. Catches documents worded differently from the question.

Query decomposition · multi-hop retrieval not in plan

Break a compound question ("Which of our customers in Germany use product X?") into sub-questions answered in sequence, each retrieval using the previous answer.

Query routing not in plan

Decide per question which source or index to search (product docs, tickets, a SQL database, the web), or whether to retrieve at all, often with a small classifier or LLM call.

Self-query · text-to-SQL not in plan

Self-query: an LLM turns "papers from 2023 about GPUs" into a semantic query plus a metadata filter. Text-to-SQL: an LLM writes a database query to answer questions over structured data. Both let RAG reach structured data.

ColBERT · late interaction not in plan

Store one vector per token rather than per chunk, and score by matching each query token to its best document token (MaxSim). More accurate than a single vector, cheaper than a cross-encoder, but needs more storage.

Knowledge graph not in plan

Data stored as entities and the relations between them (Alice works at Acme). GraphRAG extracts one from documents with an LLM so it can answer questions that need connecting facts across many documents.

Corrective RAG · Self-RAG not in plan

Patterns where the model checks its retrieved context before answering: if documents look irrelevant it rewrites the query, searches again or searches the web (CRAG); Self-RAG trains the model to decide when to retrieve and to critique its own output.

Context compression not in plan

Trimming retrieved passages to the sentences that matter before they go into the prompt, cutting tokens and distraction. Done by an LLM, a small extractive model, or a reranker at sentence level.

LLM reranking (listwise) W21

Asking an LLM to order a set of candidate passages by relevance in one call. Slower and costlier than a cross-encoder but sometimes more accurate on hard queries.

Context precision · context recall not in plan

RAG metrics (popularized by RAGAS). Context precision: how much of what was retrieved is actually relevant. Context recall: how much of the information needed for the answer was retrieved.

RAG triad W4, W24

Three checks that together locate a RAG failure: context relevance (did search find the right material?), groundedness (is the answer supported by it?), answer relevance (does it answer the question?).

Web search APIs: Tavily · Exa · Brave · Bing not in plan

Search engines with APIs built for LLMs, returning cleaned page content rather than links. Used to give RAG and agents fresh information from the web.

7.6Measuring RAG

recall@k W4, W21

For what fraction of test questions does the passage containing the answer appear in the top k results? recall@5 = 0.8 means 80% of the time. It measures retrieval alone, without the LLM.

Gold passage · test questions W4

Your 30–50 hand-written questions, each paired with the passage that actually answers it. They're the ground truth for recall@k.

MRR · nDCG not in plan

Ranking metrics that also reward putting the right passage higher. MRR (mean reciprocal rank) averages 1 ÷ rank of the first correct hit. nDCG handles graded relevance.

Groundedness · faithfulness W22, W24

Is every claim in the answer supported by the retrieved text? An answer can be correct but ungrounded (from the model's memory), or grounded but wrong (bad retrieval). Usually scored by an LLM judge claim by claim.

Answer relevance · citations W24

Answer relevance: does the answer address the question asked? Citations: the answer points to the chunks it used, which makes groundedness checkable by people too.

Index build time · query latency · cost per 1,000 queries W39

The scale metrics: how long a full re-index takes, p50 and p99 search time, and total cost (embedding, reranking, LLM) per thousand questions.

GraphRAG · agentic RAG not in plan

Variants you'll hear about. GraphRAG builds a knowledge graph of entities and relations from the corpus. Agentic RAG lets an agent decide when and what to search, possibly several times per question.

08Evals and benchmarks

Automated scoring of model output, so a change is measured rather than guessed. Lives in evals/, W5–6, W23–25, W41–42. Correctness tests for Forge's own code live in Forge's test suite (architecture rule 4).

8.1Harness and scorers

Eval (vs test) W5

A unit test passes or fails on exact behaviour. An eval scores outputs that vary, over many examples, and reports a rate. You compare rates between versions instead of expecting 100%.

Eval dataset W5, W24

A file (usually JSONL, one example per line) of inputs, expected answers and metadata. It's code: versioned, reviewed and never changed silently.

Harness · runner W5

The program that sends each example to an endpoint, records the output, applies scorers and writes a results file. Yours calls any OpenAI-compatible URL, so the same run works against Forge, vLLM or a hosted API.

Scorers: exact match · contains · rubric W5

Exact match: equal after normalizing case, spaces and punctuation. Contains: the expected string appears. Numeric tolerance: numbers within a margin (important for financial answers). Rubric: a checklist of criteria each worth points.

Golden set · hand labelling W6

Examples you label yourself (good/bad, with reasons). They're the ground truth everything automated is checked against.

8.2LLM-as-judge

LLM-as-judge W6

A model grades an answer against a rubric. Pointwise: score one answer. Pairwise: pick the better of two. It scales where hand labelling can't, but only once you've shown it agrees with you.

Judge agreement · Cohen's kappa W6

The fraction of your 50 hand labels the judge matches. Cohen's kappa corrects that for chance: two raters who always say "good" agree 90% if 90% of answers are good, yet kappa would be 0.

Judge biases W24

Known failure modes: position bias (prefers the first option), verbosity bias (prefers longer answers), self-preference (prefers its own model family). Swap orders and test for them.

8.3Regression and release

Regression evals in CI · baseline W23

Every prompt or model change runs the eval suite and compares with saved baseline scores; the build fails if a score drops by more than a set threshold.

Noise · confidence interval · bootstrap not in plan

With 50 questions, one answer is 2 percentage points, so small changes are noise. A bootstrap (re-sampling your examples many times) gives a confidence interval; only act on differences outside it.

Dataset versioning W24

Each eval dataset has a version, and results record which version they used, so scores are only compared on the same questions.

Numerical equivalence (Forge) W25

Does the KV cache, CUDA graph or custom kernel change the output? Compare logits with a tolerance and check greedy tokens match. bf16 can occasionally flip a near-tie, so explain any mismatch rather than ignore it. These live as Forge tests.

Eval-gated release W42

A new model or prompt ships only if it beats the current one on the test set by a stated margin, enforced automatically.

Offline vs online evals not in plan

Offline: a fixed dataset before release. Online: scoring a sample of real traffic after release (often with the same judge), which catches drift.

promptfoo · Inspect · DeepEval · RAGAS · Braintrust not in plan

Existing eval tools. Build yours first to understand the parts, then compare with these in your write-up.

8.4Methodology and metrics

Benchmark D157

A fixed, public eval set with a standard scoring method, used to compare models (MMLU, SWE-bench). Your own eval sets measure your task; benchmarks measure general ability.

Contamination not in plan

Benchmark questions (or answers) leaking into a model's training data, so it scores well by memory rather than skill. Hard to rule out for web-trained models; one reason new benchmarks keep appearing and why private eval sets matter.

Saturation not in plan

A benchmark is saturated when top models all score near the maximum, so it can no longer tell them apart (GSM8K, HellaSwag, original MMLU).

Goodhart's law not in plan

"When a measure becomes a target, it ceases to be a good measure." Optimizing hard for one eval score tends to find shortcuts. Watch several metrics and read real outputs.

pass@k not in plan

For code: the probability that at least one of k generated solutions passes the tests. pass@1 is the usual headline; it is estimated from n > k samples to reduce noise.

BLEU · ROUGE not in plan

Older metrics that count overlapping words or n-grams between output and a reference text. BLEU for translation, ROUGE for summaries. Cheap, but they reward wording rather than meaning and correlate poorly with quality for LLM output.

BERTScore · semantic similarity not in plan

Comparing output and reference by embedding similarity instead of exact word overlap, so paraphrases still score well.

Reference-based vs reference-free evaluation W5

Reference-based: compare output with a known correct answer. Reference-free: judge output on its own against criteria (helpful, safe, grounded in given context), as most LLM-as-judge checks do. Open-ended tasks often have no single reference.

Pairwise comparison · win rate not in plan

Show a judge (human or LLM) two outputs for the same input and ask which is better. The win rate of model A over B is the share of comparisons A wins. Easier and more consistent than absolute 1–10 scores.

Elo · Bradley–Terry rating not in plan

Systems that turn many pairwise wins and losses into one score per player (or model), as in chess. Chatbot Arena fits a Bradley–Terry model to millions of human votes.

Human evaluation · annotation guidelines W6

People rating or labelling outputs. Guidelines (definitions, examples, edge cases) make different raters agree; without them, human scores are noisy. Expensive, so used to build golden sets and to check LLM judges.

Error analysis W22, W27

Reading failed cases by hand, grouping them into categories (wrong retrieval, format error, refusal, hallucination) and counting each. The highest-value eval activity: it tells you what to fix next.

Eval-driven development W23, W42

Writing the eval before changing the prompt, model or pipeline, then using its score to decide whether the change ships, like test-driven development for model behaviour.

Statistical significance · sample size not in plan

With 100 test questions, a 2-point score change is often noise. Use paired comparisons on the same questions, bootstrap confidence intervals, and enough examples (often several hundred) before claiming one version is better.

Calibration not in plan

Whether a model's confidence matches its accuracy: of answers given at 80% confidence, about 80% should be right. Well-calibrated scores let you decide when to trust an answer or escalate to a human.

Prompt sensitivity not in plan

Scores can swing by several points from small changes in prompt wording, answer format or few-shot examples. Report the exact prompt with any score and do not compare numbers from different harnesses.

Online evaluation · A/B test not in plan

Measuring a change on real traffic: show version A to some users and B to others, and compare metrics (thumbs-up rate, task completion, retention). The final word, but slow and only for changes safe to ship.

Capability evals · safety evals not in plan

Capability evals measure what a model can do (maths, coding, agent tasks). Safety evals measure what it will or should not do (harmful help, deception, dangerous capabilities in bio or cyber). Labs run both before every release.

8.5Public benchmarks

MMLU-Pro · GPQA not in plan

Harder successors to MMLU. MMLU-Pro uses ten answer options and harder reasoning questions. GPQA (Diamond) is graduate-level biology, physics and chemistry questions that experts can answer and skilled non-experts with web access cannot.

Humanity's Last Exam (HLE) not in plan

About 2,500 very hard expert-written questions across many subjects, designed in 2025 to be the last closed-ended academic benchmark before saturation.

MATH · AIME · FrontierMath not in plan

Maths benchmarks of rising difficulty. MATH: competition problems. AIME: the US invitational exam, used to compare reasoning models. FrontierMath: unpublished research-level problems.

HumanEval · MBPP not in plan

Early code benchmarks: write a short Python function from a docstring, scored by unit tests (pass@k). Now saturated and largely replaced.

SWE-bench · SWE-bench Verified not in plan

Real GitHub issues from Python repositories: the model (as an agent) must produce a patch that makes the hidden tests pass. Verified is a human-checked subset of 500 tasks. The standard measure of coding agents.

LiveCodeBench · Terminal-Bench not in plan

LiveCodeBench collects new competitive-programming problems over time to avoid contamination. Terminal-Bench tests agents doing real tasks in a command-line environment.

HellaSwag · ARC · WinoGrande not in plan

Older commonsense and science multiple-choice benchmarks (sentence completion, grade-school science, pronoun resolution). Saturated for big models, still used to sanity-check small or quantized ones.

TruthfulQA not in plan

Questions built around common misconceptions, testing whether a model repeats popular falsehoods.

IFEval not in plan

Instruction-following eval with automatically checkable rules ("answer in under 100 words", "use no commas", "end with this phrase").

MT-Bench · AlpacaEval · Arena-Hard not in plan

Chat-quality benchmarks scored by a strong LLM judge: multi-turn questions (MT-Bench) or win rate against a reference model (AlpacaEval, Arena-Hard). Cheap stand-ins for human preference.

Chatbot Arena · LMArena not in plan

A public site where people chat with two anonymous models side by side and vote for the better answer; votes become Elo-style rankings. The most cited human-preference leaderboard, also criticized for being gameable by style.

Agent benchmarks: τ-bench · GAIA · WebArena · OSWorld not in plan

Benchmarks of multi-step tool use. τ-bench: customer-service tasks with tools and policies. GAIA: research questions needing browsing and tools. WebArena: tasks on realistic websites. OSWorld: tasks operating a full desktop.

BFCL (Berkeley Function-Calling Leaderboard) not in plan

Measures how accurately models produce tool calls: picking the right function, filling arguments correctly, knowing when not to call.

ARC-AGI not in plan

François Chollet's grid puzzles, each needing a new abstract rule inferred from a few examples. Built to measure fluid reasoning rather than knowledge; hard for models that score highly elsewhere.

HELM · Open LLM Leaderboard not in plan

Broad benchmark suites. HELM (Stanford) evaluates many models on many scenarios and metrics (accuracy, calibration, bias, efficiency). The Open LLM Leaderboard (Hugging Face) ranked open models with lm-evaluation-harness.

8.6Evals in practice

Trajectory evaluation not in plan

For agents, scoring the path as well as the result: did it call the right tools, in a sensible order, without wasted steps or unsafe actions?

Synthetic eval data not in plan

Using an LLM to generate test questions (and sometimes answers) from your documents or specs, then having people check a sample. Fast way to get coverage; can miss what real users ask.

Production data flywheel not in plan

Turning real traffic into improvements: log requests, sample failures and user complaints, label them, and add them to eval and training sets, so the system improves with use.

Labelling tools: Label Studio · Argilla not in plan

Tools for humans to label data and review model outputs in a queue, with guidelines and agreement tracking. LangSmith, Langfuse and Braintrust have built-in annotation queues too.

OpenAI Evals · simple-evals not in plan

OpenAI's open-source eval framework and its small reference implementations of popular benchmarks, often used to reproduce reported scores.

Assertion-based tests W5

Deterministic checks on LLM output that run like unit tests: valid JSON, contains the required field, no banned words, under a length limit. Cheap, fast and run first, before any LLM judge.

Eval cost and speed not in plan

Each eval run costs tokens and time, especially with LLM judges. Keep a small fast subset for every pull request and run the full set nightly or before release.

09Agents and tool use

A loop where the model calls tools step by step to finish a task. Lives in agents/, W12–13, W31–32, W47–48.

9.1The loop

Agent W12

A program that gives a model a task and a list of tools, runs whatever tool the model asks for, appends the result to the conversation and repeats until the model gives a final answer or a limit is hit.

Tool calling · function calling W12

The model is given tool definitions (name, description, parameters as JSON Schema) and can reply with a tool_calls entry naming a tool and its JSON arguments instead of text. Your code validates the arguments, runs the tool and sends back a role: "tool" message with the result.

JSON Schema W12

A standard way to describe the shape of JSON data (types, required fields, allowed values). Used both to tell the model what arguments a tool takes and to check what it sent.

Structured output · constrained decoding not in plan

Forcing a model's output to match a schema by masking out, at every step, any token that would break it. Done inside the engine (libraries like xgrammar and Outlines), which makes it a strong stretch feature for Forge.

ReAct not in plan

"Reason + act": the model alternates writing a short thought and taking an action. It's the paper behind the modern agent loop.

Step limit · budget W12

Hard caps on steps, tokens and cost per task so a confused agent can't loop forever.

Task set · task success rate W13, W48

Your 20 tasks, each with a checkable end state (a number, a file, a fact). The success rate is the agent's headline metric, compared across passes.

9.2Tool calls in detail

Tool definition · tool description W12

What the model is told about a tool: a name, a plain-language description of what it does and when to use it, and a JSON Schema for its arguments. The description is a prompt: vague descriptions cause wrong tool choices.

tool_choice not in plan

A request field controlling tool use: auto (model decides), required (must call some tool), none, or a specific named tool.

Parallel tool calls not in plan

The model asks for several independent tool calls in one turn (look up three cities' weather at once); the app runs them concurrently and returns all results together.

Tool result · observation W12

The output of a tool, sent back to the model as a tool-role message tied to its call ID. In ReAct terms it is the observation the next step reasons over. Large results must be trimmed to fit the context.

Code interpreter · code execution tool W31

A tool that runs model-written code (usually Python) in a sandbox and returns the output, letting the model do exact maths, data analysis and file processing.

Web search · fetch tools not in plan

Tools that let an agent search the web and read pages, giving it fresh information. Every fetched page is untrusted input and a possible prompt-injection source.

Tool-call parsing (engine side) not in plan

Open models emit tool calls as specially formatted text (JSON inside tags, or special tokens); the serving engine must parse it into the API's tool_calls field, model family by model family. vLLM and SGLang ship a parser per family.

WhySomething Forge would need for its API to support agents with open models.

9.3Reliability

Idempotency W31

A tool call is idempotent if running it twice has the same effect as once (reading a file: yes; sending an email: no). Only idempotent steps are safe to retry blindly.

Checkpointing · resumable runs W31

Saving the agent's state (messages, completed steps) after each step, so a crash resumes from the last checkpoint instead of starting over.

Durable execution not in plan

Frameworks (e.g. Temporal) that make every step of a workflow automatically checkpointed and retryable. Know the term when discussing agent reliability.

Sandboxed code execution W31

Running model-written code in an isolated Docker container: no network, CPU, memory and time limits, a read-only filesystem, and a non-root user. The model's code is untrusted input.

9.4Workflows and agent patterns

Workflow vs agent W11, W12

A workflow runs LLM calls along a path fixed in code. An agent lets the model decide the next step and when it is done. Workflows are more predictable and cheaper; use an agent only when the steps cannot be known in advance.

Augmented LLM not in plan

The basic building block: one model call with access to retrieval, tools and memory. Workflows and agents are compositions of these.

Routing (workflow pattern) W11

A first call classifies the input and sends it to a specialized prompt, tool set or model (refund question → refunds flow). Same idea as model routing in the gateway, applied inside an app.

Parallelization: sectioning · voting not in plan

Run several LLM calls at once and combine them: sectioning splits a task into independent parts; voting runs the same task several times and takes the majority or best.

Orchestrator–workers not in plan

A lead model breaks a task into subtasks at run time, hands each to a worker call or subagent, and combines their results. Used by deep-research systems.

Evaluator–optimizer · reflection not in plan

One call produces an answer, another critiques it against criteria, and the first revises; repeat until good enough. Reflection is the single-model version: the model reviews its own output.

Plan-and-execute not in plan

The agent first writes an explicit plan (a list of steps), then carries it out step by step, revising the plan when results surprise it. Keeps long tasks on track and makes progress visible.

Multi-agent system not in plan

Several agents with different roles, prompts or tools working together (researcher, writer, reviewer), passing messages or work between them. Powerful for broad tasks; costs more tokens and is harder to debug than one agent.

Subagents · handoffs not in plan

A subagent is an agent started by another to do a focused piece of work in its own fresh context and report back a summary, keeping the parent's context small. A handoff transfers the whole conversation to a different agent (sales → support).

Agent memory not in plan

What an agent keeps beyond one context window. Short-term: the current conversation and scratchpad. Long-term: facts, preferences and past outcomes stored in files or a database and retrieved when relevant.

Context compaction not in plan

When a long-running agent's context fills up, summarize older turns and tool results into a short note and continue with that, so the task can outlast one context window.

Scratchpad · to-do list not in plan

A place (a file, a list in the context) where the agent writes its plan, progress and notes as it works, so it does not lose track during long tasks.

Long-horizon tasks not in plan

Tasks needing dozens to hundreds of steps over minutes or hours (implement a feature, research a market). Small per-step error rates compound, so reliability, checkpointing and recovery matter most here.

Agent harness · scaffolding W12

The code around the model that makes it an agent: the loop, tool execution, context management, permissions, retries and logging. The same model performs very differently in different harnesses.

9.5Permissions and oversight

Least privilege W32, W48

Give each agent only the tools and permissions its task needs. An injected instruction can't misuse a tool the agent doesn't have.

Human-in-the-loop approval W48

Pausing before risky tool calls (sending, deleting, paying) until a person approves. It's the strongest defence against an agent doing harm.

Permission modes · approval policies W48

Rules for which actions an agent may take on its own and which need a person's approval (read files freely; ask before deleting, paying or sending). Usually set per tool and per risk level.

Audit log not in plan

A tamper-resistant record of every action an agent took, with its inputs, outputs and who approved it, so incidents can be investigated afterwards.

Agent budget · kill switch W12

Hard limits on spend, tokens, wall-clock time or steps per task, and a way to stop a running agent immediately. Agents in loops can burn money fast.

9.6Frameworks and protocols

MCP (Model Context Protocol) not in plan

An open standard for exposing tools and data to models: a tool provider runs an MCP server, and any MCP client (an agent, an IDE, a chat app) can use it. Now the common way tools are packaged.

MCP server · client · transports not in plan

An MCP server exposes tools (actions), resources (readable data) and prompts (templates). The client inside an app or agent connects to it and passes those to the model. Servers run locally over stdio or remotely over streamable HTTP, usually with OAuth.

A2A (Agent2Agent protocol) not in plan

An open protocol, started by Google, for agents from different vendors to discover each other's capabilities and delegate tasks. MCP connects an agent to tools; A2A connects agents to agents.

Agent skills not in plan

Packaged folders of instructions, scripts and reference files that an agent loads only when a task needs them, extending what it can do without bloating every prompt (introduced by Anthropic in 2025 and adopted by other tools).

LangGraph · OpenAI Agents SDK · Claude Agent SDK · Pydantic AI not in plan

Agent frameworks. Building your own loop first is the point of the plan; afterwards, know what these add (state graphs, handoffs, tracing).

CrewAI · AutoGen · smolagents not in plan

More agent frameworks. CrewAI: teams of role-playing agents. AutoGen (Microsoft): multi-agent conversations. smolagents (Hugging Face): minimal agents that write Python code as their actions.

9.7Kinds of agents

Coding agents not in plan

Agents that read and edit a codebase, run commands and tests, and open pull requests: Claude Code, OpenAI Codex, Cursor's agent, GitHub Copilot's coding agent, Devin and others. The most commercially successful agent category so far.

Computer use not in plan

An agent that operates a graphical desktop like a person: it sees screenshots and sends mouse clicks and keystrokes. Works with any application, but slower and less reliable than API tools.

Browser agents not in plan

Agents that navigate websites (click, fill forms, read pages), either via screenshots or the page's structure. Examples: OpenAI's ChatGPT agent, Claude in Chrome, Browser Use, Playwright-based agents.

Deep research agents not in plan

Agents that run many searches, read dozens of sources and write a cited report over several minutes (ChatGPT, Gemini and Claude all offer one). A clear example of the orchestrator–workers pattern.

Voice agents not in plan

Agents you talk to on the phone or in an app, combining speech recognition, an LLM with tools, and speech synthesis (or one speech-to-speech model) under tight latency limits, roughly under a second per reply.

Background (asynchronous) agents not in plan

Agents that work on a task for minutes or hours without a person watching (often in a cloud sandbox) and report back with a result, such as a pull request.

10Safety, security and guardrails

What can go wrong when an LLM is connected to users, data and tools, and how teams defend against it. Security failures here are concrete: leaked data, unwanted actions, harmful output. Agents in W32 and W48 are where you build these defences.

10.1Attacks

Prompt injection (direct · indirect) W32

Text that tries to override the agent's instructions. Direct: typed by the user. Indirect: hidden in content the agent reads (a retrieved document, a web page, a tool result). Indirect is the dangerous one for agents with tools.

Jailbreak not in plan

A prompt crafted to make a model ignore its safety training and produce content it would normally refuse, through role-play ("pretend you are DAN"), hypotheticals, encodings or long persuasion. Different from prompt injection: a jailbreak attacks the model's rules; injection attacks the app's instructions.

Many-shot jailbreaking · adversarial suffix not in plan

Two systematic jailbreak techniques. Many-shot: fill a long context with hundreds of fake dialogues where an assistant complies, then ask. Adversarial suffix (GCG): an automatically optimized string of odd tokens appended to a request that flips the model into complying.

Data exfiltration not in plan

An attacker, usually through indirect injection, makes an agent send private data out: in a tool call, an email, or a markdown image URL with secrets in its query string that the user's browser then loads.

Lethal trifecta not in plan

Simon Willison's rule of thumb: an agent with (1) access to private data, (2) exposure to untrusted content, and (3) a way to send data out can be made to leak that data. Remove any one of the three to break the attack.

System prompt leakage not in plan

Users getting the model to reveal its hidden instructions ("repeat everything above"). Assume system prompts can leak; never put secrets in them.

Insecure output handling not in plan

Trusting model output as safe input to something else: running generated SQL or shell commands, or rendering generated HTML (cross-site scripting). Treat model output like user input.

Excessive agency not in plan

Giving an agent more tools, permissions or autonomy than its task needs, so a mistake or an injection can do real damage. Fixed by least privilege and human approval for risky actions.

Data poisoning · backdoors not in plan

Planting crafted data in training or retrieval sources (a web page, a shared document, a fine-tuning set) so the model later misbehaves, possibly only when a hidden trigger phrase appears.

Model extraction · training-data extraction not in plan

Model extraction: copying a model's behaviour by querying it heavily and training on the answers. Training-data extraction: getting a model to reproduce memorized private text from its training data.

Denial of wallet not in plan

Abusing an LLM endpoint with long or looping requests to run up the owner's bill. Defended with rate limits, token quotas and budgets per user.

OWASP Top 10 for LLM Applications not in plan

The OWASP security project's list of the most important LLM-app risks: prompt injection, sensitive information disclosure, supply chain, data and model poisoning, improper output handling, excessive agency, system prompt leakage, vector and embedding weaknesses, misinformation, and unbounded consumption. A good checklist for a design review.

10.2Defences

Guardrails W32

Checks on what goes into and comes out of the model: PII redaction, blocked topics, output schema validation, tool-argument validation.

PII redaction W32

Detecting and masking personally identifiable information (names, emails, phone and card numbers) before it reaches a model or a log. Regexes catch formats; NER models (e.g. Microsoft Presidio) catch names.

Injection test set · block rate W32

A set of attack inputs, each run against each defence. The block rate is the share stopped. Also measure the false-positive rate on normal inputs.

Input and output filters · moderation W32

Classifiers that screen user input and model output for categories such as violence, self-harm, sexual content or hate before passing them on. OpenAI's moderation endpoint is a free hosted example.

Safety classifiers: Llama Guard · ShieldGemma · Prompt Guard not in plan

Small open models trained to label prompts and responses as safe or unsafe by category (Llama Guard, ShieldGemma), or to detect injection and jailbreak attempts (Prompt Guard). Run them in your gateway or agent loop.

Guardrail frameworks: NeMo Guardrails · Guardrails AI not in plan

Libraries for declaring checks around LLM calls: allowed topics, required output formats, PII and toxicity filters, with automatic retries or refusals when a check fails.

Instruction hierarchy not in plan

Training models to rank instructions by source (system prompt above user, user above tool results and documents), so text inside a fetched web page cannot override the developer's rules. Helps against injection; does not fully solve it.

Spotlighting · data marking not in plan

Clearly separating untrusted content in the prompt (wrapping it in tags, encoding it, or marking every line) and telling the model never to follow instructions found inside it. A partial defence.

Dual-LLM pattern · CaMeL not in plan

Architectural defences against injection: a privileged model that plans and calls tools never sees untrusted text; a quarantined model reads untrusted text but has no tools. Google DeepMind's CaMeL formalizes this with data-flow tracking.

Red teaming W32

Deliberately attacking your own system (by hand, with attack datasets, or with automated attacker models) to find failures before others do. Tools: PyRIT, garak, promptfoo's red-team mode.

Refusal · over-refusal not in plan

A refusal is the model declining a request. Over-refusal is declining harmless requests that merely look risky ("how do I kill a Python process?"). Both are measured in safety evals.

Secrets management for agents not in plan

Keep API keys and credentials out of prompts and model-visible context: tools hold the secrets and the model only asks the tool to act. Anything in the context can leak.

10.3Alignment, risk and policy

Alignment not in plan

Making a model's behaviour match what its developers and users intend: helpful, honest, harmless. Covers training methods (RLHF, Constitutional AI) and the research question of keeping much more capable future systems aligned.

Sycophancy not in plan

The model telling users what they want to hear: agreeing with wrong claims, praising weak work, changing a correct answer when challenged. A side effect of training on human approval.

Bias and fairness not in plan

Models can treat people differently by gender, race, nationality or language because of patterns in their training data. Measured with paired prompts that differ only in such attributes.

Toxicity not in plan

Offensive, hateful or abusive output. Measured with classifiers (such as Perspective API) and benchmarks of provocative prompts.

Responsible scaling policies · frontier safety frameworks not in plan

Labs' published commitments to test each new model for dangerous capabilities (bioweapons, cyberattacks, autonomous replication) and to apply stronger safeguards before release if thresholds are crossed. Anthropic's RSP, OpenAI's Preparedness Framework, Google DeepMind's Frontier Safety Framework.

System card not in plan

A detailed document released with a model describing its safety testing, red-teaming results, known risks and mitigations. Longer and more safety-focused than a model card.

EU AI Act not in plan

The European Union's AI law, phased in from 2024 to 2027: bans some uses, imposes duties on "high-risk" systems, and sets transparency and safety obligations on providers of general-purpose AI models.

NIST AI RMF · ISO/IEC 42001 not in plan

Voluntary frameworks for managing AI risk: the US NIST AI Risk Management Framework, and ISO/IEC 42001, an AI management-system standard companies can be certified against.

Data privacy: GDPR · zero data retention W32

GDPR (EU) governs personal data: legal basis, purpose limits, deletion rights. For LLM apps, it matters what you send to providers and log. Zero data retention agreements mean the provider stores no prompts or outputs.

SOC 2 not in plan

A widely requested audit report showing a company controls security, availability and confidentiality properly. Enterprise customers usually ask any AI vendor, including an inference provider, for one.

Watermarking · content provenance (C2PA) not in plan

Watermarking hides a statistical signal in generated text or images so they can later be detected as AI-made (Google's SynthID). C2PA attaches signed metadata recording how media was created and edited.

Deepfakes not in plan

Realistic generated images, audio or video of real people saying or doing things they did not. A major misuse concern for image, video and voice models.

Copyright and training data not in plan

Open legal questions over whether training on copyrighted text, code and images is permitted, and over outputs that reproduce protected work. Several major lawsuits and licensing deals are shaping the answer.

11Observability

Recording what happened in every request (steps, time, tokens, cost) so you can see where time and money go. Lives in observability/, W8–9, W26–27, W43–44.

11.1Logs, metrics, traces

Logs · metrics · traces W8–9

The three kinds of telemetry. Logs: one record per event. Metrics: numbers aggregated over time (rates, percentiles). Traces: the timed tree of steps inside one request.

Structured logging W8

Logging each request as one JSON object with fixed fields (request ID, trace ID, model, input and output tokens, TTFT, latency, cost, status) instead of free text, so logs can be queried.

Request ID · trace ID W8–9

Unique IDs that tie together every log line and span for one request across services.

OpenTelemetry (OTel) W9, W43

The vendor-neutral standard and SDKs for producing traces, metrics and logs. Instrument once, then send the data to Jaeger, Grafana or any vendor.

Trace · span · parent span W9

A trace is one request's whole journey. A span is one timed step in it, with a name, start, end, attributes and a parent. The parent links form a tree, drawn as the waterfall above.

Context propagation W10, W43

Passing the trace ID from service to service (in HTTP, the traceparent header) so every service's spans land in the same trace.

OTLP · Collector not in plan

OTLP is OpenTelemetry's wire protocol. The Collector is a process that receives OTLP, batches and filters it, and forwards it to back-ends.

GenAI semantic conventions not in plan

OpenTelemetry's standard attribute names for LLM calls, such as gen_ai.request.model and gen_ai.usage.input_tokens. Using them makes your traces readable by other tools.

Jaeger W9

An open-source trace store and viewer. Run it in Docker locally and open the waterfall for any request.

11.2Tracing in more depth

Span attributes · span events W9

Attributes are key–value facts attached to a span (gen_ai.request.model, prompt_tokens, tenant). Events are timestamped points inside a span (first token arrived, retry started).

Trace sampling: head · tail not in plan

Storing every trace is expensive, so keep a sample. Head sampling decides at the start (keep 10% at random). Tail sampling decides after the trace finishes, so you can keep all errors and slow requests.

Latency breakdown W43

Splitting one request's time into its parts (gateway, retrieval, queue wait, prefill, decode, tool calls) using spans, so you can see which part to speed up. Forge's queue, prefill and decode spans feed this.

Exemplars not in plan

A link from a point on a metric chart (say a slow bucket of the latency histogram) to an example trace from that moment, so you can jump from "p99 is high" to one actual slow request.

Grafana Tempo · Loki not in plan

Grafana's trace store (Tempo) and log store (Loki), which pair with Prometheus for metrics to give one open-source stack for all three signals.

11.3Metrics and dashboards

Prometheus · scraping D121, W26

A time-series database that scrapes (polls) each service's /metrics endpoint every few seconds and stores the numbers. Queried with PromQL.

Counter · gauge · histogram D121

Counter: only goes up (requests served, tokens generated); you graph its rate. Gauge: goes up and down (queue length, KV usage %). Histogram: counts observations into buckets (TTFT), from which histogram_quantile estimates p50 and p99.

Grafana D121, W26

A dashboard tool that charts Prometheus queries. Your Forge dashboard shows tokens/s, TTFT and TPOT percentiles, queue depth and GPU utilisation.

Label cardinality not in plan

Each distinct combination of metric labels creates a new time series. Putting user IDs or prompts in labels creates millions of series and breaks Prometheus. High-cardinality detail belongs in traces and logs.

GPU utilisation · DCGM W26

nvidia-smi's "utilisation" means the share of time any kernel was running, not how hard the GPU worked. A GPU can show 100% while mostly waiting on memory. DCGM exporter gives better per-SM metrics to Prometheus.

Alerting · Alertmanager W27

Rules that fire when a metric crosses a threshold for a while, e.g. error rate > 2% for 5 minutes or p99 TTFT > 2 s. Prometheus's Alertmanager routes them to you.

SLI · SLO · error budget not in plan

SLI: the measured indicator (p99 TTFT). SLO: its target. Error budget: the allowed amount of failure (1 − SLO); when it's spent, stop shipping risky changes.

11.4Running a service

Four golden signals · RED · USE not in plan

Checklists of what to monitor. Google SRE's golden signals: latency, traffic, errors, saturation. RED for request-driven services: rate, errors, duration. USE for resources such as GPUs: utilization, saturation, errors.

PromQL W26

Prometheus's query language, for example histogram_quantile(0.99, rate(ttft_seconds_bucket[5m])) for p99 TTFT over the last five minutes. Every Grafana panel on Prometheus data is a PromQL query.

Commercial observability: Datadog · New Relic · Honeycomb not in plan

Hosted platforms that collect logs, metrics and traces (most accept OpenTelemetry), with dashboards and alerting. What many employers run instead of a self-hosted stack.

ELK · OpenSearch (logs) not in plan

ELK is Elasticsearch, Logstash and Kibana: a common stack for storing and searching logs. OpenSearch is the open-source fork.

Continuous profiling · eBPF not in plan

Sampling where CPU (and sometimes GPU) time goes in production all the time, at low overhead (Pyroscope, Parca). eBPF is the Linux technology that lets such tools observe programs without changing them.

Incident · on-call · postmortem not in plan

An incident is an outage or serious degradation. On-call engineers are paged to respond. A postmortem afterwards records the timeline, root cause and fixes, without blame. MTTR (mean time to recovery) tracks how fast you recover.

Runbook not in plan

Written steps for handling a known alert ("TTFT p99 high: check queue depth, then KV usage, then..."), so whoever is on call can act without guessing.

Synthetic monitoring not in plan

Sending scripted test requests to production on a schedule (one tiny chat completion every minute) to detect outages before users report them.

11.5Cost and failure analysis

Cost per request · per million tokens W8, W26

Hosted APIs charge per million input tokens and per million output tokens at different prices. For Forge: GPU cost per hour ÷ tokens generated per hour. Comparing the two decides when self-hosting pays.

Cost attribution W44

Tagging every span with customer and feature, then summing cost per customer and per feature. That tells you which customers are profitable.

Failure taxonomy W27

Sorting bad answers into categories using their traces: retrieval missed, model ignored context, hallucination, bad format, timeout, refusal. The biggest category is the next thing to fix.

Langfuse · LangSmith · Phoenix · Helicone not in plan

LLM-specific observability products. Langfuse and Phoenix are open source. Know what they do so you can say why you built yours.

11.6LLM-specific observability

Prompt and response logging W8

Storing the full input and output of each model call, the most useful debugging data an LLM app has. Needs redaction, access control and a retention limit because it contains user data.

Token usage tracking W8

Recording input, output, cached and reasoning tokens per request, model, feature and tenant: the basis of cost reports, quotas and capacity planning.

User feedback signals not in plan

Thumbs up/down, edits, regenerations, copy events and abandoned sessions logged against the trace, giving cheap, noisy quality labels from real use.

Online quality monitoring not in plan

Running automatic checks (an LLM judge, groundedness or format checks) on a sample of live traffic, so quality drops show up on a dashboard like latency does.

Drift not in plan

Change over time that hurts quality: data drift (users start asking different things), model drift (a hosted provider silently updates a model), or index drift (documents change). Caught by online monitoring and periodic evals.

Session and agent traces W12, W43

Grouping all model and tool calls of one conversation or one agent run into a single trace tree, so you can replay what the agent saw and did at each step.

Engine metrics D121

What a serving engine exports beyond request latency: running and waiting requests, KV cache usage, preemptions, prefix-cache hit rate, batch size and tokens per second. vLLM's names are the de facto reference; Forge's /metrics provides the same kind.

OpenLLMetry · W&B Weave · Arize not in plan

More LLM-observability tools. OpenLLMetry (Traceloop): OpenTelemetry instrumentation for LLM libraries. Weave (Weights & Biases) and Arize combine tracing with evals.

12Gateway and production (LLMOps)

One endpoint in front of every model. It decides which backend gets each request, and handles caching, retries and fallbacks. Lives in gateway/, W10–11, W28–30, W45–46.

12.1Proxy basics

LLM gateway · reverse proxy W10

A server that accepts OpenAI-format requests and forwards them to a chosen backend (Forge, vLLM, a hosted API), streaming the response back. SSE must be passed through without buffering, or TTFT is lost.

Backend registry W10, W30

Config listing each backend: URL, models served, price, limits, health. Backends are just URLs (architecture rule 1).

Retries · exponential backoff · jitter W10

Retry failed calls after waiting 1 s, 2 s, 4 s… (exponential backoff) plus a random amount (jitter) so clients don't retry in sync. Retry only safe failures (429, 503, connection errors), and never after part of a stream has reached the user.

Timeouts W10

Separate limits for connecting, for the first token (TTFT) and for the whole response. A stuck backend then fails fast instead of holding the request forever.

Fallbacks W29

An ordered list of backends: if the first fails or its breaker is open, try the next (e.g. Forge → hosted small model → hosted large model).

Health checks W29

Periodic cheap requests (e.g. /v1/models) to know which backends are up before sending real traffic.

Streaming usage accounting W10

Counting tokens on streamed responses for cost logging. With OpenAI-format streams, stream_options: {include_usage: true} adds a final chunk with token counts.

12.2Routing, caching, protection

Model routing W11, W30

Choosing a backend per request. Rule-based: by prompt length, keywords or a task tag ("easy" → small model). Cost-based: cheapest backend meeting a quality bar, using observability numbers. Evals measure the quality lost; logs measure the cost saved.

Learned routers · RouteLLM not in plan

A small classifier trained to predict whether the cheap model will do well enough on a given request. RouteLLM is the best-known open project.

Exact cache W28

Key = hash of the normalized request (model, messages, sampling settings); a hit returns the stored response. Only safe when output is deterministic (temperature 0 or a fixed seed).

Semantic cache W28

Embed the prompt; if a cached prompt is more similar than a threshold, return its answer. It catches rephrasings but risks wrong hits ("capital of France" vs "capital of Germany"), so measure the hit rate and the wrong-hit rate.

Three kinds of caching W28

Easy to confuse. Response caching (gateway) skips the model entirely. Prefix caching (Forge) reuses KV for a shared prompt start but still generates. Provider prompt caching is the hosted API's version of prefix caching, sold as a discount.

Rate limiting · token bucket W29, W45

A token bucket holds up to C tokens and refills at R per second; each request takes some, and is rejected (429) when the bucket is empty. Apply it per API key, both to requests per minute and LLM tokens per minute.

Circuit breaker W29

After N consecutive failures a backend's breaker opens and requests skip it immediately. After a cool-down it goes half-open and lets one trial through; success closes it, failure reopens it.

Chaos testing W29

Breaking things on purpose (killing a backend, adding latency) to prove that retries, breakers and fallbacks work.

Load balancing · prefix-aware routing not in plan

Spreading requests across replicas (round robin, least outstanding requests). Prefix-aware routing sends requests with the same prompt start to the same Forge replica so its prefix cache gets hits. This is where gateway and engine meet.

Multi-tenancy · quotas · noisy neighbour W45

One gateway shared by many customers. Each API key maps to a tenant with its own quotas and limits, and isolation ensures one tenant can't exhaust capacity for others (the noisy neighbour problem) or see their cached data.

LiteLLM · OpenRouter · Portkey · Envoy AI Gateway not in plan

Existing gateways: LiteLLM (open-source proxy), OpenRouter (hosted marketplace), Portkey (commercial), Envoy AI Gateway (built on the Envoy proxy).

12.3More gateway vocabulary

API keys · virtual keys W45

The gateway issues its own keys to teams and apps (virtual keys), each mapped to permissions, budgets and rate limits, while the real provider keys stay inside the gateway.

Budgets · spend limits W45

Per key or per team caps on money or tokens per day or month, enforced by the gateway, with alerts before they are hit.

Model aliases not in plan

Clients ask for a stable name (fast, smart, support-bot) and the gateway maps it to a real model, so models can be swapped without client changes.

Model cascade not in plan

Try a cheap model first and escalate to an expensive one only when a check (confidence, a validator, a judge) says the cheap answer is not good enough.

KV-cache-aware routing D170

Sending a request to the replica most likely to already hold its prefix in KV cache (same conversation or same system prompt), so prefix caching works across a fleet. NVIDIA Dynamo, llm-d and SGLang's router do this.

Hedged requests not in plan

Sending the same request to a second backend if the first has not answered within a short delay, and using whichever replies first. Cuts tail latency at the price of some duplicate work.

Request coalescing not in plan

When identical requests arrive at once, run the model once and give every caller the same result.

Kong · Cloudflare AI Gateway not in plan

More gateways. Kong: a general API gateway with AI plugins. Cloudflare AI Gateway: a hosted proxy adding caching, rate limits and logging in front of model providers.

12.4Deployment

Kubernetes · Ray Serve · KServe not in plan

Production orchestration you'll be asked about in system design: Kubernetes schedules containers across machines; Ray Serve and KServe deploy and scale model servers on top.

Pod · Deployment · Service (Kubernetes) not in plan

Kubernetes basics. A pod is one or more containers scheduled together on a node; a Deployment keeps N identical pods running and replaces failed ones; a Service gives them one stable network address with load balancing.

Helm not in plan

A package manager for Kubernetes: a chart is a template of all the resources an app needs, installed with values you choose (model name, GPU count). vLLM and most serving stacks publish charts.

GPU scheduling in Kubernetes not in plan

Pods request GPUs like CPU or memory (nvidia.com/gpu: 1); the NVIDIA device plugin or GPU Operator exposes them. MIG and time-slicing let several pods share one GPU.

Autoscaling · HPA · KEDA D170

Adding and removing replicas as load changes. The HPA (horizontal pod autoscaler) scales on CPU or custom metrics; KEDA scales on queue length or other external signals. For LLMs, scale on queue depth or KV usage, not CPU.

Cold start not in plan

The delay before a new replica can serve: starting the container, loading tens of gigabytes of weights, compiling kernels and CUDA graphs. Often minutes, which makes fast scale-up hard; fixed with weight caching, snapshots and warm pools.

Scale to zero · serverless GPU not in plan

Running no replicas when idle and starting one on demand, paying only while running (Modal, RunPod Serverless, Replicate, cloud functions with GPUs). Cheap for spiky traffic, at the cost of cold starts.

Model registry · MLflow not in plan

A catalogue of model versions with their metadata, eval results and stage (staging, production). MLflow is the common open-source tool; clouds have their own.

Canary · blue–green · shadow deployment not in plan

Ways to release safely. Canary: send a small share of traffic to the new version and watch metrics. Blue–green: run old and new side by side and switch traffic at once, keeping the old ready for rollback. Shadow: copy real traffic to the new version without using its answers.

Feature flags not in plan

Switches in config that turn a feature, prompt or model on for some users without a deploy, making rollouts and rollbacks instant.

Rollback not in plan

Returning to the previous version quickly when a release misbehaves. Requires keeping the old model, prompt and config versions deployable.

Infrastructure as code: Terraform not in plan

Describing servers, clusters and networks in versioned config files (Terraform, Pulumi) and applying them automatically, rather than clicking in a cloud console.

BentoML · Modal · Replicate not in plan

Platforms for packaging and deploying models as APIs with autoscaling, without running your own Kubernetes. Common for small teams and demos.

12.5Capacity and cost

Capacity planning D170, W46

Working out how many GPUs a service needs: expected requests per second × tokens per request, divided by the tokens per second one replica sustains within the latency SLO, plus headroom for peaks and failures.

Cost per token (self-hosted) W26

GPU cost per hour ÷ tokens produced per hour at realistic load. Comparing it with API prices tells you when self-hosting pays off; it only beats APIs at high, steady utilization.

Utilization vs latency trade-off D124

Larger batches raise throughput and cut cost per token but raise each user's latency. The SLO sets how far you can push it, which is why goodput is the right metric.

Reserved · on-demand · spot capacity not in plan

Ways to buy cloud GPUs. On-demand: pay by the hour, no commitment. Reserved: commit for months or years for a big discount. Spot: cheap spare capacity that can be taken back at short notice, suited to batch and evals.

FinOps W44

The practice of tracking, attributing and optimizing cloud spend across teams. For AI products, GPU and token costs usually dominate the bill.

13.2Datacenter accelerators

NVIDIA A100 (Ampere) not in plan

The 2020 datacenter GPU that trained the first wave of LLMs: 40 or 80 GB of HBM, about 2 TB/s of memory bandwidth, about 312 dense bf16 TFLOPS. Still widely rented.

NVIDIA H100 · H200 (Hopper) D87

The 2022–2024 workhorse. H100: 80 GB HBM3, about 3.35 TB/s, about 990 dense bf16 TFLOPS, FP8 support, TMA and warp specialization (what FlashAttention-3 targets). H200: the same chip with 141 GB at about 4.8 TB/s, which helps memory-bound decode.

NVIDIA B200 · GB200 · B300 (Blackwell) not in plan

The 2025 generation: two dies per package, 180–288 GB of HBM, about 8 TB/s, and FP4 (NVFP4) tensor cores. GB200 pairs two B200s with a Grace CPU. Rubin is the next generation, announced for 2026.

GB200 NVL72 · rack-scale systems not in plan

A single rack of 72 Blackwell GPUs all joined by NVLink switches so they behave like one giant GPU for communication. Built for serving and training the largest MoE models with wide expert and tensor parallelism.

DGX · HGX not in plan

NVIDIA's standard server designs: 8 GPUs fully connected by NVLink/NVSwitch in one box. DGX is NVIDIA's own branded system; HGX is the board other server makers build around. "An 8×H100 node" usually means one of these.

TFLOPS spec sheets · sparsity D44

Peak throughput numbers from vendors are best-case figures, often quoted "with sparsity" (2:4 structured sparsity, which doubles the number but which real LLMs rarely use). Divide by two for dense, and expect 50–70% of that in practice.

MIG (multi-instance GPU) not in plan

Splitting one A100/H100-class GPU into up to seven isolated smaller GPUs, each with its own memory and compute, so small models or tenants can share it safely.

Transformer Engine not in plan

NVIDIA's library for running transformer layers in FP8 (and FP4 on Blackwell) with automatic per-tensor scaling, used in training and in TensorRT-LLM.

AMD Instinct MI300X · MI355X · ROCm not in plan

AMD's datacenter GPUs, with more HBM per GPU than NVIDIA's equivalents (192 GB on MI300X, 288 GB on MI355X). ROCm is AMD's software stack (its CUDA equivalent, with HIP as the CUDA-like language); PyTorch, vLLM, SGLang and Triton all support it.

Google TPU not in plan

Google's own AI chips (Tensor Processing Units), built around large matrix units and fast chip-to-chip links, programmed through JAX or PyTorch/XLA. Gemini is trained and served on them; rentable only on Google Cloud.

AWS Trainium · Inferentia not in plan

Amazon's own chips for training (Trainium) and inference (Inferentia), programmed with the Neuron SDK. Anthropic is a major Trainium user.

Groq LPU · Cerebras · SambaNova not in plan

Specialized inference chips. Groq's LPU and Cerebras's wafer-sized chip keep weights in on-chip SRAM, avoiding the HBM bandwidth limit, and reach very high tokens per second per user.

Apple silicon · unified memory not in plan

Macs share one pool of memory between CPU and GPU (up to 512 GB on high-end models), so they can hold models far larger than any consumer graphics card, at lower bandwidth than datacenter GPUs. Popular for local inference with MLX and llama.cpp.

Consumer GPUs: RTX 4090 · 5090 not in plan

High-end gaming cards (24 GB and 32 GB) widely used for local inference and research. Same architecture family as your 4060, with about 4× its memory and memory bandwidth.

Power · TDP not in plan

Thermal design power: how many watts a chip draws at full load (about 115 W for your 4060, 700 W for an H100, about 1,000 W or more for B200-class). Datacenter power supply, not chip supply, is now often the limit on AI capacity.

13.3Interconnects and clusters

NVSwitch not in plan

A switch chip that connects every GPU in a server (or an NVL72 rack) to every other at full NVLink speed, instead of point-to-point links. Makes all-reduce across 8 or 72 GPUs fast.

Scale-up vs scale-out not in plan

Scale-up: GPUs joined by very fast links inside one server or rack (NVLink, about 900 GB/s per GPU on H100). Scale-out: many servers joined by a network (InfiniBand or Ethernet, about 50 GB/s per GPU). Tensor parallelism stays inside the scale-up domain.

InfiniBand · RoCE not in plan

High-bandwidth, low-latency networks that link GPU servers in a cluster. InfiniBand (NVIDIA/Mellanox) is the traditional choice; RoCE (RDMA over Converged Ethernet) brings the same capability to Ethernet, which hyperscalers increasingly use.

RDMA · GPUDirect not in plan

RDMA (remote direct memory access): one machine reads or writes another's memory over the network without involving either CPU. GPUDirect RDMA does this straight to and from GPU memory, which KV transfer in disaggregated serving relies on.

NIXL not in plan

NVIDIA's inference transfer library, which moves KV cache blocks between GPUs and machines over the fastest available path (NVLink, RDMA, storage). Used by Dynamo and vLLM for disaggregated serving.

Slurm not in plan

The job scheduler most GPU clusters and supercomputers use: you submit a job requesting N nodes and GPUs, it waits in a queue and runs when they free up. Training teams use it more than Kubernetes.

Ray not in plan

A Python framework for distributing work across a cluster (tasks, actors, shared objects). Used for distributed data processing, RL training loops and serving (Ray Serve), and vLLM uses it for multi-node setups.

Neoclouds: CoreWeave · Lambda · Crusoe · Nebius D145

GPU-focused cloud providers that rent large NVIDIA clusters, often cheaper or more available than the big three clouds. The main suppliers of AI compute outside AWS, Google and Azure.

13.4Distributed training

DDP (DistributedDataParallel) not in plan

PyTorch's standard data parallelism: each GPU holds a full model copy, processes different data, and gradients are averaged with all-reduce after each backward pass, overlapped with computation.

ZeRO · DeepSpeed not in plan

ZeRO removes the redundancy in data parallelism by sharding optimizer states (stage 1), gradients (stage 2) and the weights themselves (stage 3) across GPUs, so much bigger models fit. DeepSpeed is Microsoft's training library that introduced it.

FSDP (Fully Sharded Data Parallel) not in plan

PyTorch's built-in version of ZeRO stage 3: each GPU stores only a shard of every layer and gathers the full layer just before using it. FSDP2 is the current version.

3D parallelism not in plan

Combining data, tensor and pipeline parallelism (plus context and expert parallelism for long sequences and MoE) to train models across thousands of GPUs. Megatron-LM, torchtitan and DeepSpeed implement it.

Pipeline bubble · micro-batches not in plan

With pipeline parallelism, GPUs sit idle while waiting for the first activations to arrive and the last gradients to return (the bubble). Splitting each batch into many micro-batches and clever schedules (1F1B, interleaved) keep the bubble small.

Context parallelism · ring attention not in plan

Splitting one very long sequence across GPUs. In ring attention, each GPU holds part of the sequence's keys and values and passes them around a ring, so attention over a million tokens fits in total memory.

MFU (model FLOPs utilization) not in plan

Useful FLOPs actually achieved divided by the hardware's peak. Large training runs typically reach 35–50%. Inference decode MFU is far lower, because decode is memory-bound.

Fault tolerance · stragglers not in plan

In runs on thousands of GPUs, hardware fails every few hours. Training must checkpoint often and restart quickly, and detect stragglers (slow GPUs that hold back every synchronized step).

torchtitan · Megatron-Core not in plan

Reference large-scale training codebases. torchtitan is PyTorch's clean, native one (FSDP2, TP, PP, context parallelism, FP8). Megatron-Core is NVIDIA's library under Megatron-LM and NeMo.

JAX · XLA not in plan

JAX is Google's array library with automatic differentiation and transformations such as jit and vmap. XLA is the compiler under it that fuses operations for TPUs and GPUs. Google, and some labs, train in JAX rather than PyTorch.

14Multimodal models

Models that see, hear, speak and draw. Most frontier models now take images (and often audio) as input, and serving them adds new steps before the familiar prefill and decode.

14.1Vision and vision-language models

ViT (vision transformer) not in plan

A transformer applied to images: cut the image into fixed-size patches (say 14×14 pixels), embed each patch as a token, and run ordinary attention. Replaced CNNs as the standard image encoder.

CLIP · contrastive image–text training not in plan

OpenAI's 2021 model that trains an image encoder and a text encoder together so matching image–caption pairs get similar vectors. Gives zero-shot image classification and is the vision encoder or text encoder inside many later models. SigLIP is Google's improved variant.

VLM (vision-language model) not in plan

An LLM that also takes images: a vision encoder turns an image into vectors, a small projector maps them into the LLM's embedding space, and they enter the sequence as image tokens. Examples: GPT-4o, Claude, Gemini, Llama 3.2 Vision, Qwen2.5-VL, LLaVA.

LLaVA not in plan

An influential 2023 open recipe for building a VLM cheaply: connect a pretrained CLIP encoder to a pretrained LLM with a projector, and train mostly the projector on image–instruction data.

Image tokens · dynamic resolution not in plan

How many tokens an image costs depends on its size: models tile large images into crops or process them at native resolution, so one screenshot can be anything from a few hundred to a few thousand tokens.

WhyImages can dominate prefill cost and KV cache size in multimodal serving.

Native multimodality · early fusion not in plan

Training one model on interleaved text, image and audio tokens from the start (early fusion) rather than attaching a separate encoder to a finished text model. Gemini and GPT-4o-class models work this way.

Document understanding · OCR-free not in plan

VLMs reading documents, charts, forms and screenshots directly from pixels, without a separate OCR step. Increasingly used for document parsing in RAG.

Multimodal embeddings not in plan

Embedding models that place images and text (and sometimes audio and video) in one vector space, so a text query can retrieve images and vice versa (CLIP-style models, Cohere and Voyage multimodal embeddings).

Encoder cache · multimodal serving not in plan

Serving VLMs adds work before prefill: decoding and resizing images, running the vision encoder, and caching its outputs so the same image is not encoded twice. vLLM and SGLang schedule this separately from text tokens.

14.2Image and video generation

Diffusion model not in plan

A generator trained to reverse a noising process: start from pure random noise and remove noise step by step (often 20–50 steps), guided by a text prompt, until an image appears. The dominant approach for images and video.

Latent diffusion · Stable Diffusion not in plan

Running diffusion in a small compressed latent space produced by a VAE rather than on full pixels, which is far cheaper. Stable Diffusion (Stability AI) made this open and popular in 2022.

U-Net · DiT (diffusion transformer) not in plan

The networks that predict the noise to remove at each step. Early models used a convolutional U-Net; newer ones (Stable Diffusion 3, FLUX, Sora-class video models) use a diffusion transformer, which scales better.

Classifier-free guidance (CFG) not in plan

At each step, predict once with the prompt and once without, and push the result further in the direction the prompt implies. A guidance scale sets how strongly the image follows the prompt. Doubles compute per step.

Flow matching · rectified flow not in plan

A newer training formulation that learns a straight-line path from noise to data, allowing good images in fewer steps. Used by Stable Diffusion 3 and FLUX.

Text-to-image models: FLUX · Midjourney · Imagen · GPT Image not in plan

Leading image generators. FLUX (Black Forest Labs) has open-weight versions; Midjourney, Google's Imagen and OpenAI's GPT Image are closed. GPT Image generates autoregressively within a multimodal LLM rather than by pure diffusion.

ControlNet · LoRA for images · inpainting not in plan

Ways to steer image generation. ControlNet conditions on an edge map, pose or depth image; image LoRAs teach a style or character; inpainting regenerates only a masked region.

Video generation: Sora · Veo · Kling not in plan

Diffusion transformers that generate video clips from text or images, treating video as patches in space and time. Extremely compute-heavy to serve: one clip can take minutes on many GPUs.

Step distillation · few-step generation not in plan

Training a diffusion model to produce good images in 1–4 steps instead of 20–50 (SDXL Turbo, LCM), which cuts generation latency dramatically.

14.3Speech and audio

ASR (speech-to-text) · Whisper not in plan

Automatic speech recognition turns audio into text. Whisper (OpenAI, open weights) is an encoder–decoder transformer that does multilingual transcription and translation and is the default open choice.

TTS (text-to-speech) · voice cloning not in plan

Generating natural speech from text. Modern TTS models (ElevenLabs, OpenAI, open models such as Kokoro and XTTS) can imitate a voice from a few seconds of sample audio, which also enables fraud.

Audio tokens · neural codec not in plan

A neural codec (such as EnCodec or Mimi) compresses audio into a sequence of discrete tokens, so a transformer can read and generate speech the way it handles text.

Speech-to-speech models · realtime APIs not in plan

Models that take audio in and produce audio out directly, without separate transcription and synthesis steps, giving lower latency and keeping tone of voice (GPT-4o realtime, Gemini Live, Moshi). Served through streaming realtime APIs over WebSockets or WebRTC.

VAD · turn detection · barge-in not in plan

Voice-agent mechanics. Voice activity detection finds when someone is speaking; turn detection decides they have finished; barge-in lets the user interrupt the agent mid-sentence, which must cancel generation and playback immediately.

Speaker diarization not in plan

Labelling who spoke when in a recording with several speakers ("speaker 1: ... speaker 2: ...").

14.4Beyond text and images

Any-to-any models not in plan

Single models that accept and produce any mix of text, images, audio and video. The direction most frontier labs are moving in.

VLA (vision-language-action) models not in plan

Models for robots that take camera images and an instruction and output motor actions, built from VLMs (Google's RT-2 and Gemini Robotics, Physical Intelligence's π0).

World models not in plan

Models that learn how an environment changes in response to actions and can simulate it, generating playable or explorable video worlds (Google's Genie). Used for training agents and robots in simulation.
